01

프로젝트 요약

BACKGROUND

A부서(실시간 심사 문서 처리)와 B부서(과거 축적 문서 일괄 처리), 두 부서를 대상으로 AgileSoda AIOCR 엔진(TwinReader)을 실제 업무 시스템에 연동하는 중간 API 서버 2종을 설계·구현했다. OCR 엔진 자체를 개발한 것이 아니라, 문서별 분류/추출 스키마 설계부터 API 연동, 결과 가공, 배치 운영까지 문서 처리 파이프라인 전 구간을 담당했다.

담당 업무 (부서별)

A부서 · 실시간 연동

수기로 입력하던 심사 항목을 AIOCR로 자동 추출·기입하는 구조로 전환. 실시간 REST API 설계, Nexacro 연동 대응, 이력 관리를 담당했다.

B부서 · 배치 연동

과거 축적 문서를 일괄 OCR 처리해 학습용 raw 데이터로 적재. 배치 스크립트, crontab 스케줄, 분석 트리거 API를 담당했다.

A부서 — 실시간 연동 구조

SYNC-LIKE POLLING
  • TwinReader는 내부적으로 비동기(콜백 기반)로 동작하지만, 콜백 수신 전까지 처리 상태를 폴링하며 대기하는 구조로 클라이언트에는 동기 응답처럼 제공
  • 요청 단위로 중복 여부와 처리 상태를 관리하고, 완료 후 결과를 재조회할 수 있는 API를 함께 구현
  • Nexacro 프론트엔드 연동을 위한 Multipart 업로드 호환 처리
  • MyBatis / MySQL 기반 이력 관리

B부서 — 배치 연동 구조

FIRE-AND-FORGET
  • 실시간 응답이 필요하지 않은 대신 대량 문서를 반복 처리해야 했기에 배치 스크립트 기반의 완전 비동기(fire-and-forget) 구조로 설계
  • 문서를 일정 건수 단위로 그룹핑해 순차 트리거, 그룹 간 대기 시간을 두어 처리 지연 누적 방지
  • 처리 / 강제 종료·재기동 / 결과 전송을 별도 스크립트로 분리하고 crontab으로 평일·주말 스케줄을 다르게 운영
  • 가공 결과를 CSV로 변환·유형별 분류 후 내부 서버로 전송하는 파이프라인까지 연결
03

트러블슈팅

A부서

TwinReader의 비동기 콜백 구조 때문에, 실시간성이 필요한 화면에서 즉시 응답이 불가능했다

원인

OCR 분석 결과가 콜백으로 비동기 전달되는 구조라, 요청-응답 한 사이클 안에서 결과를 바로 돌려줄 수 없었음

해결 과정

콜백 수신 전까지 처리 상태를 폴링하며 대기하는 구조를 구현하고, 요청 단위 중복·상태 관리와 재조회 API를 함께 설계

결과

클라이언트 입장에서는 동기 응답처럼 실시간 심사 화면에 결과를 반영할 수 있게 됨

B부서

대량 문서 그룹을 쉬지 않고 연속 호출하면 처리가 누적되며 오류가 발생했다

원인

반복 배치 호출 시 이전 그룹의 처리가 끝나기 전에 다음 그룹이 트리거되어 지연이 누적되는 구조적 위험

해결 과정

문서를 일정 건수 단위로 그룹핑하고, 그룹 간 대기 시간을 둔 배치 간격을 직접 설계. 처리/재기동/결과전송을 스크립트로 분리해 crontab으로 스케줄링

결과

대량 문서 처리 시 발생하던 지연 누적 오류를 완화

A부서

Nexacro 프론트엔드에서 표준 Multipart 업로드가 정상 동작하지 않았다

원인

A부서가 사용하는 Nexacro 프론트엔드의 요청 방식이 표준적인 Spring Multipart 처리 방식과 호환되지 않음

해결 과정

호환성 문제의 원인을 분석하고 이를 처리할 수 있도록 서버 측 업로드 처리 로직을 조정

결과

Nexacro 환경에서도 정상적으로 문서 업로드·연동이 가능해짐

공통

TwinReader 내부 포맷(JSON) 결과를 부서가 실제로 쓸 수 있는 형태로 바꿔야 했다

원인

OCR 결과가 TwinReader 내부 포맷으로 반환되어, 불필요한 메타데이터가 섞여 있고 부서별로 필요한 항목도 서로 달랐음

해결 과정

부서별 문서 종류·요구 항목을 분석해 JSON 기반 분류/추출 스키마를 설계하고, 불필요한 메타데이터를 제거·재구성하는 가공 로직을 JavaScript로 구현. B부서는 최종 CSV 변환까지 파이프라인화

결과

정제된 JSON/CSV로 각 부서가 바로 활용 가능, 신규 문서 유형 추가 시에도 스키마 확장으로 대응 가능한 구조 확보

  • B부서

    모델 개발 데이터 기반 마련. 과거 문서를 자동 OCR 처리해 raw 데이터로 적재하는 구조를 구축, 이후 자체 모델 개발의 학습 데이터 기반을 마련했다.

05

회고 · 배운 점

DESIGN

같은 엔진, 다른 두 개의 설계

동일한 AIOCR 엔진을 연동하더라도, 부서의 업무 특성(실시간성 vs. 대량 처리)에 따라 완전히 다른 아키텍처가 필요하다는 것을 체감했다. 요구사항을 먼저 "동기적 사용자 경험이 필요한가"와 "처리량이 우선인가"로 구분해 접근한 것이 설계 방향을 잡는 데 핵심이었다.

ASYNC

비동기 콜백을 다루는 감각

외부 엔진의 비동기 콜백 구조를 그대로 노출하지 않고, 상태 폴링과 재조회 API로 감싸 클라이언트 경험을 단순하게 만드는 패턴을 익혔다. 이 경험은 이후 외부 시스템 연동 설계에서 반복적으로 활용하는 접근이 됐다.

OPERATIONS

운영까지 고려한 배치 설계

배치는 "돌아가는 것"과 "안정적으로 운영되는 것"이 다르다는 걸 배웠다. 처리/재기동/전송 스크립트를 분리하고 crontab 스케줄을 요일별로 다르게 가져간 것은, 실제 장애 상황을 가정하고 복구 단위를 최소화하기 위한 선택이었다.

SCOPE

맡은 범위를 명확히 하기

HTTPS 전환 등 사내 시스템 담당자와 협업이 필요했던 영역은 주도적으로 해결한 부분이 아니었다. 포트폴리오를 정리하면서, 직접 설계·구현한 영역과 협업으로 진행된 영역을 구분해 기록하는 것의 중요성도 다시 확인했다.
