PROJECT 02 · 2023.11 — 2024.01 · 개인 프로젝트

실시간 알림 서버

초당 수천 건의 이벤트를 받아 접속 중인 사용자에게 지연 없이 전달하는 WebSocket 기반 알림 서버를 직접 설계하고 구현했습니다.

GitHub ↗ Live Demo ↗

OVERVIEW

기존 폴링 방식(3초마다 알림 조회)은 서버 부하가 크고 실시간성이 떨어졌습니다. 이 문제를 직접 해결해보고 싶어 WebSocket 기반 알림 서버를 개인 프로젝트로 구현했습니다. 동시 접속 1만 명을 가정한 부하 테스트까지 진행했습니다.

PROBLEM

  • 폴링 방식은 사용자 수가 늘수록 서버 요청량이 선형적으로 증가
  • 서버 재시작 시 모든 클라이언트 연결이 끊기고 재연결 폭주 발생
  • 다중 서버 환경에서 특정 서버에 연결된 사용자에게만 메시지 전달되는 문제

ARCHITECTURE

서버 간 메시지 브로드캐스트를 위해 Redis Pub/Sub을 도입해, 어느 서버에 연결되어 있어도 알림을 받을 수 있도록 구성했습니다.

Event Source │ ▼ [Notify API] ──publish──▶ Redis Pub/Sub │ │ ▼ ┌──────────┼──────────┐ [WS Server A] [WS Server B] [WS Server C] │ │ │ Client 1,2 Client 3 Client 4,5

KEY DECISIONS

재연결 폭주를 어떻게 막았는가. 클라이언트 재연결 로직에 지수 백오프(exponential backoff)와 지터(jitter)를 적용해, 서버 재시작 직후 동시 재연결이 몰리는 현상을 완화했습니다.

왜 Socket.io 대신 순수 WebSocket을 선택했는가. 폴백(polling fallback) 기능이 필요 없는 환경이었고, 메시지 포맷을 직접 제어하며 오버헤드를 최소화하고 싶어 직접 구현하는 방향을 택했습니다.

TROUBLESHOOTING

부하 테스트 중 동시 접속 5천 명을 넘기면서 메모리 사용량이 급증하는 현상을 발견했습니다. 프로파일링 결과 연결이 끊긴 소켓의 이벤트 리스너가 정리되지 않고 누적되는 메모리 누수였고, 연결 종료 시 리스너를 명시적으로 해제하도록 수정해 해결했습니다.

RESULTS

10,000 동시 접속 테스트
~120ms 평균 알림 전달 지연
-90% 서버 요청 수 (폴링 대비)

수치는 예시입니다. 실제 부하 테스트 도구(nGrinder, k6 등)로 측정한 로그/그래프를 캡처해 첨부하면 신뢰도가 올라갑니다.

TECH STACK

  • Node.js
  • ws (WebSocket)
  • Redis Pub/Sub
  • Docker
  • k6 (부하테스트)
