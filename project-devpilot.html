01

프로젝트 요약

문제. GitHub 활동·학습 기록·보유 기술·로드맵을 결합한 AI 분석은 외부 API 호출이 포함돼 즉시 응답하기 어렵습니다. 사용자가 응답을 기다리는 동안 재요청하면 동일 분석이 중복 실행될 수도 있습니다.

설계. 요청을 DB 기반 비동기 Job으로 접수하고 상태 조회 API로 결과를 제공합니다. 동일 사용자·멱등성 키의 중복 생성을 MySQL UNIQUE 제약으로 막고, 실패 결과까지 조회 가능하게 저장했습니다.

현재 범위

GitHub와 자체 학습 데이터 연동 및 Career Gap Analysis 구현. Velog·Notion 등 추가 데이터 소스는 아직 구현 전입니다. 프론트엔드는 기능 사용을 위한 React 대시보드로 구성했습니다.

02

백엔드 설계

비동기 Job과 상태 전이

POST 요청 시 PENDING을 저장하고 202 Accepted와 analysisId를 반환합니다. 전용 ThreadPoolTaskExecutor에서 RUNNING으로 전이해 분석을 수행하며, 성공은 COMPLETED, 오류는 FAILED와 오류 메시지로 기록합니다. 클라이언트는 GET API로 상태와 결과를 조회합니다.

멱등성의 최종 방어선은 DB

(user_id, idempotency_key) UNIQUE 제약을 두고 INSERT 충돌을 중복 요청의 정상 흐름으로 처리했습니다. 생성 트랜잭션을 별도 경계(REQUIRES_NEW)로 분리해 제약 위반 이후 트랜잭션이 오염되지 않게 하고, 동일 키 요청에는 기존 Job ID를 돌려줍니다. 신규 Job에 대해서만 분석을 실행합니다.

외부 호출과 저장의 책임 분리

GitHub REST·GraphQL 호출과 JPA 저장 작업을 분리했습니다. 외부 호출 중 DB 트랜잭션을 길게 유지하지 않도록 GithubSyncWriter에 저장 책임을 두고, Spring AOP가 적용되는 호출 경계를 별도 Bean으로 구성했습니다.

운영 구조

GitHub OAuth2 로그인과 Redis 세션을 적용했습니다. MySQL 스키마는 Flyway로 관리하고 Hibernate ddl-auto: validate로 검증합니다. EC2의 Docker Compose에 백엔드·MySQL·Redis를 배포하고 S3·CloudFront로 프론트엔드를 제공합니다.

03

핵심 문제 해결과 검증

01 · 동시 요청에서도 분석 한 건만 생성

문제: 조회 후 INSERT 방식은 동시 요청 사이에 중복 Job을 만들 수 있습니다. 해결: 사용자·멱등성 키의 UNIQUE 제약과 독립적인 생성 트랜잭션을 사용했습니다. 검증: Testcontainers의 실제 MySQL·Redis 환경에서 10개 스레드가 동일 키를 동시에 요청해도 레코드가 1개 생성되는 통합 테스트를 작성했습니다.

02 · 실패와 지연 로딩까지 테스트

AI 호출 실패 시 Job이 FAILED로 남는지 통합 테스트로 확인했습니다. 연관 컬렉션이 비어 있을 때 드러나지 않던 LazyInitializationException을 실제 연관 데이터로 재현하고 Repository Fetch Join으로 수정했습니다. MySQL 스키마는 Flyway 마이그레이션과 Hibernate validate로 확인했습니다.

03 · 외부 API 장애의 전파 범위 제한

GitHub와 Gemini 호출에 타임아웃, 재시도(최대 3회), Circuit Breaker를 적용하고 Gemini 동시 호출에는 Bulkhead를 설정했습니다. 인증 실패 및 재시도가 부적절한 4xx는 재시도 대상에서 제외했습니다. AOP self-invocation으로 정책이 적용되지 않는 구간은 별도 Bean으로 분리해 테스트했습니다.

04

배포·성능 검증

세션 유지와 CI/CD

Spring Session Redis 적용 후 컨테이너 재생성 시 로그인 유지 여부를 확인했습니다. GitHub Actions에서 빌드·테스트·이미지 게시를 수행하고 EC2는 이미지를 받아 재기동하도록 구성해 서버 내 빌드 부담을 제거했습니다.

부하테스트와 수평 확장 실험

k6의 800 VU 시나리오에서 단일 t3.micro 환경 p95 1.24초를 측정했습니다. Terraform으로 ALB·ASG 백엔드 3대 환경을 구성한 실험에서는 p95 176.48ms, 처리량 599.6 req/s를 측정했습니다. 이는 인프라 구성도 함께 달라진 비교이며, ASG 환경의 오류율은 1.10%였습니다. ASG 1대의 오류 및 재시작 원인은 조사 중입니다. 확장 인프라는 실험 후 제거했고 현재 상시 운영 구조가 아닙니다.

관측과 남은 과제

Actuator·Micrometer·Prometheus·Grafana로 HTTP·JVM·DB·Job 지표를 관찰하도록 구성했습니다. 부하 상황의 인스턴스 재시작과 health check 영향을 재검증하고 있습니다. 현재 CloudFront 사용자 구간은 HTTPS지만 EC2 오리진은 HTTP인 구조로, 정식 HTTPS 전환이 남아 있습니다.

05

설계에서 배운 점

동시성은 테스트와 제약으로 검증

중복 요청의 정확성은 애플리케이션의 사전 조회에만 맡기지 않고 DB 제약과 실제 동시 요청 테스트로 확인했습니다.

실패 경로도 서비스의 일부

비동기 Job은 완료 결과뿐 아니라 실패 상태를 조회할 수 있어야 하고, 외부 API 장애가 전체 요청 처리에 전파되지 않도록 경계를 정해야 한다는 점을 확인했습니다.
