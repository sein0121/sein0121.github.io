01

프로젝트 요약

배경. GitHub 활동과 학습 기록, 보유 기술 및 로드맵이 흩어져 있어 성장 현황과 다음 학습 방향을 함께 보기 어려웠습니다. 이를 하나의 서비스로 모아 목표와 현재 활동을 비교하고 AI 분석 결과를 제공하고자 했습니다.

구현. GitHub OAuth 로그인과 활동 동기화, Skill·StudyLog·Roadmap 관리 API를 만들고, AI 분석 요청은 멱등성을 보장하는 비동기 Job으로 처리합니다. Flyway로 스키마를 관리하고 Testcontainers 통합 테스트와 Resilience4j 장애 대응을 적용했습니다.

운영 검증. MySQL·Redis 기반 백엔드를 AWS에 배포하고 CI/CD를 구성했습니다. Prometheus·Grafana로 지표를 수집한 상태에서 부하 실험을 다시 수행했습니다. 이전에 원인을 찾지 못했던 컨테이너 재시작 문제를 컨테이너 메모리 한도 대비 JVM 메모리 설정 문제로 판단했고, 설정 조정 후 같은 조건에서 재시작이 사라지는 것을 확인했습니다.

현재 상시 운영 구성입니다. ALB·ASG는 아래 부하 실험에서만 Terraform으로 생성했다가 제거했으며, 코드는 저장소에 남겨 같은 환경을 다시 만들 수 있습니다.

API·인증
  • GitHub OAuth2 로그인과 Spring Security 메서드 권한 검사로 본인 API와 관리자 API 분리
  • GitHub 활동 동기화와 Skill·StudyLog·Roadmap 관리 API 제공
  • 로그인 세션을 Redis(named volume + AOF)에 저장하고 배포 시 백엔드만 교체해, 재배포·Redis 재시작 후에도 로그인 유지를 운영 서버에서 재현 확인
데이터·트랜잭션
  • JPA 엔티티와 Request/Response DTO를 분리하고 상태 변경은 엔티티 메서드로 캡슐화
  • ddl-auto: update를 제거하고 Flyway로 전환. 운영 스키마 덤프로 baseline을 만들고 기존 데이터 손실 없이 적용, Hibernate는 validate만 수행
  • GitHub 외부 호출 후 별도 Writer에서 저장해, 외부 응답을 기다리는 동안 DB 커넥션을 점유하지 않음
외부 연동·안정성
  • GitHub·Gemini 호출에 타임아웃, 대기 간격과 Jitter를 둔 재시도, Circuit Breaker 적용
  • 재시도가 의미 없는 401·4xx는 즉시 실패시키고, Gemini 동시 호출은 Bulkhead로 제한해 요금·rate limit 보호
  • AI 클라이언트를 인터페이스로 분리해 공급사 의존성을 격리하고, Gemini responseSchema로 응답 구조 강제
비동기 분석
  • 요청 접수 시 202 Accepted와 Job ID를 즉시 반환하고 전용 스레드풀에서 분석
  • (user_id, idempotency_key) UNIQUE 제약으로 중복 Job 방지. 동일 키 재요청은 기존 Job ID 반환
  • 요청 수·완료·실패·대기 Job 수·대기 시간·실행 시간을 커스텀 지표로 계측

핵심 데이터 흐름

① 활동 수집GitHub REST·GraphQL 조회
② 데이터 저장MySQL의 GitHub 활동·Skill·StudyLog·Roadmap
③ 분석 요청Idempotency-Key · Job 생성 · 202 Accepted
④ 결과 조회Gemini 분석 후 상태·결과 GET 폴링

개념 흐름도입니다. 실제 테이블 관계와 컬럼을 확정한 ERD는 코드의 엔티티·Flyway 정의를 검증한 뒤 추가하는 것이 정확합니다.

03

핵심 문제 해결과 검증

01 · 분석 Job의 중복 실행 방지
  • 문제. 조회 후 INSERT 방식은 동시 요청이 모두 "없음"을 보고 중복 Job을 만들 수 있음
  • 해결. 먼저 INSERT하고 UNIQUE 위반을 정상 흐름으로 받아 기존 Job을 재조회. 생성은 REQUIRES_NEW로 분리해 제약 위반 후 트랜잭션 오염 방지
  • 검증. Testcontainers의 실제 MySQL·Redis에서 동일 키 10개 동시 요청 시 레코드 1개 생성 확인
02 · 비동기 실행 중 지연 로딩 오류
  • 문제. 운영 데이터로 분석 시 LazyInitializationException 발생. 로컬은 연관 컬렉션이 비어 있어 드러나지 않았음
  • 해결. 넓은 트랜잭션 대신 Repository Fetch Join으로 필요한 연관만 조회 시점에 로딩 (Gemini 호출 동안 커넥션 점유 방지)
  • 검증. 연관이 채워진 데이터로 통합 테스트를 만들고, 버그를 되살려 테스트가 실패하는 것까지 확인
03 · 외부 장애 대응이 실제로 동작하는가
  • 문제. 같은 클래스 내부 호출은 AOP 프록시를 거치지 않아 재시도가 무시되고, 람다 대역으로 만든 테스트는 Circuit Breaker를 우회해 항상 CLOSED
  • 해결. 페이지 조회 로직을 별도 Bean으로 분리하고, 테스트는 실제 Gemini 클라이언트에 연결 거부 주소를 주입해 진짜 AOP 경로에서 장애 재현
  • 검증. 재시도 후 Circuit Breaker OPEN 전환, AI 실패 시 Job FAILED 저장을 통합 테스트로 확인
04 · 원인 미확정이던 컨테이너 재시작
  • 문제. ASG 1대 부하 시 오류율이 급증하고 컨테이너가 로그 없이 ExitCode 0으로 재시작됨
  • 분석. 헬스체크 오판 가설을 저부하 재측정으로 기각. 유휴 상태에서도 메모리 사용률이 97%였고, JVM 플래그를 보니 Code Cache 등 Non-Heap 상한이 컨테이너 한도를 고려하지 않은 기본값이어서 부하 시 여유가 없다고 판단
  • 조치. 힙·Code Cache·Metaspace 상한을 명시하고 컨테이너 한도를 400MB에서 550MB로 상향
  • 검증. 같은 인프라·같은 k6 스크립트로 전후 비교 (04장). 두 조치 중 어느 쪽이 결정적이었는지는 분리 검증하지 않음
04

배포·성능 검증

CI/CD와 운영
  • PR마다 GitHub Actions에서 Testcontainers 포함 빌드·테스트, main 반영 시 GHCR에 이미지 게시
  • EC2는 이미지를 받아 Docker Compose로 재기동만 수행해 1GB 서버의 Gradle 빌드 OOM 제거
  • CloudFront 2-Origin으로 프론트와 API를 한 도메인에 묶어 Mixed Content·교차 사이트 쿠키 문제 해결
  • Actuator는 별도 관리 포트로 분리하고 필요한 엔드포인트만 노출, 운영 서버에는 수집 도구를 두지 않음
측정과 분석
  • k6로 DB 조회 API(/api/skills, /api/study-logs)를 측정. 단일 t3.micro는 800 VU에서 p95 1.24초. N+1이 없고 커넥션·스레드 풀 튜닝 효과가 미미했으며 CPU 사용률 포화(105~110%)를 관찰
  • Terraform으로 ALB·ASG를 구성해 확장 실험. 1대 구성에서 재시작 장애를 발견하고 Prometheus·Grafana 지표로 재조사
  • 메모리 설정 조정 후 같은 조건으로 다시 측정해 1대·3대 결과를 비교

컨테이너 재시작 원인 추적

① 증상부하 중 오류율 급증, 컨테이너 재시작 흔적
② 가설 기각헬스체크 완화 후에도 100 VU에서 재시작
③ 컨테이너 상태OOMKilled false · ExitCode 0 · 직전 로그 없음
④ 메모리트래픽 없이도 389MB / 400MB (97%)
⑤ 판단힙 상한 126MB 외에 Code Cache 상한이 약 246MB인 기본값. 한도 400MB 대비 Non-Heap 여유 부족
JAVA_TOOL_OPTIONS="-Xmx170m -XX:ReservedCodeCacheSize=48m -XX:MaxMetaspaceSize=150m" # container memory 400m → 550m

첫 시도에서 Metaspace를 96MB로 줄였다가 기동 중 OOM이 발생해 150MB로 조정했습니다. 설정은 로컬에서 같은 옵션으로 기동 검증한 뒤 반영했고, Terraform 코드에 보존되어 있습니다. 표시한 Code Cache 값은 JVM 플래그로 확인한 상한이며, 영역별 실제 사용량은 측정하지 않았습니다.

모든 수치는 Terraform으로 만든 ALB·ASG 실험 환경에서 같은 k6 스크립트로 측정했습니다. 조정은 JVM 메모리 상한 명시와 컨테이너 한도 상향(400MB → 550MB)을 함께 적용한 것이며, 상시 운영 서버와는 구성이 다릅니다. 3대로 늘렸을 때 처리량은 약 1.5배로 선형에 미치지 못했으며, 공유 MySQL 또는 부하 발생 PC의 한계로 추정하지만 계측 근거가 없어 확정하지 않았습니다. ALB·ASG는 실험 후 제거했습니다.

05

설계에서 배운 점

트랜잭션 경계는 외부 호출과 함께 설계

외부 API를 기다리는 시간과 DB 저장 시간을 분리하고, 동시성은 애플리케이션 체크가 아니라 DB 제약으로 보장했습니다. AOP 기반 기능은 호출 경로에 따라 적용되지 않을 수 있어, 테스트도 실제 프록시 경로를 거치는지 확인해야 한다는 것을 배웠습니다.

그럴듯한 가설도 데이터로 검증하기

헬스체크 오판 가설은 논리적으로 맞아 보였지만 더 낮은 부하에서도 재현되어 버렸습니다. 컨테이너 메모리 한도를 정할 때 힙만이 아니라 Code Cache·Metaspace 같은 Non-Heap 영역까지 고려해야 한다는 것, 그리고 scale-out만 했다면 개선 효과를 잘못 해석했을 수 있다는 것을 배웠습니다.

확정한 것과 추정한 것을 구분하기

3대 확장의 비선형 결과와 메모리 조치별 효과는 확정하지 못했습니다. 관측 사실과 추정을 나눠 기록하고, 다음 실험에서는 DB 지표와 JVM 영역별 메모리 사용량을 부하와 같은 시간대로 함께 남길 계획입니다.
