01

프로젝트 요약

배경. GitHub 활동과 학습 기록, 보유 기술과 로드맵이 흩어져 있어 성장 현황과 다음 학습 방향을 함께 보기 어려웠습니다. 이를 하나의 서비스로 모아 등록된 데이터에 근거한 AI 분석과 학습 추천을 제공하고자 했습니다.

설계. 시간이 걸리는 커리어 분석은 비동기 Job으로 접수하고 상태·결과를 조회하도록 구성했습니다. 멱등 키와 DB UNIQUE 제약으로 동일 요청의 중복 Job 생성을 막고, 외부 API 호출과 DB 저장 트랜잭션을 분리했습니다.

검증. 실제 MySQL·Redis를 사용하는 통합 테스트로 동시 요청을 검증하고, 모의 HTTP 응답으로 재시도 정책을 확인했습니다. 운영 서버에서는 재배포 후 로그인 유지를 확인했으며, 별도 부하 실험에서는 메모리 설정 조정과 백엔드 확장 전후를 비교했습니다.

브라우저는 같은 HTTPS 도메인으로 접근

현재 운영은 단일 EC2 구성입니다. ALB·ASG는 별도 확장 실험에만 사용했으며, DB·Redis는 기존 EC2를 공유했습니다. CloudFront를 통한 브라우저 HTTPS 접근과 Origin 구간 암호화는 별개이며, Origin HTTPS는 추가 적용 과제입니다.

API·인증
  • GitHub OAuth2로 로그인하고 Redis Session에 로그인 상태 저장
  • 로그인 Principal에서 사용자 ID를 가져와 데이터 소유권을 검사하고, 관리자 API에는 메서드 권한 제어 적용
  • Skill·StudyLog·Roadmap 관리와 GitHub 활동 동기화 API 제공
데이터·트랜잭션
  • 엔티티와 Request/Response DTO를 분리하고, 변경 의도를 나타내는 엔티티 메서드 사용
  • GitHub 외부 호출 후 별도 Writer에서 프로필·저장소·기여 기록을 하나의 트랜잭션으로 반영
  • 기존 운영 DB를 Flyway baseline으로 이력 관리에 편입하고, 이후 변경은 버전별 SQL로 관리; Hibernate는 validate로 매핑 확인
비동기 분석·중복 제어
  • PENDING 작업을 별도 Writer에서 커밋한 뒤 전용 스레드풀에 실행 요청
  • 202 Accepted와 Job ID를 반환하고 PENDING → RUNNING → COMPLETED/FAILED 상태·결과 조회 제공
  • (user_id, idempotency_key) UNIQUE 제약으로 동일 키의 중복 Job 생성을 막고, 재요청에는 기존 작업 반환
외부 호출·장애 대응
  • 타임아웃, 대기 간격과 Jitter를 둔 Retry, Circuit Breaker 적용
  • Gemini는 연결 실패·5xx만 재시도하고 4xx·429는 즉시 실패하도록 정책 통일
  • Bulkhead로 인스턴스별 Gemini 동시 호출 수 제한; 클라이언트를 인터페이스로 분리해 연동 코드와 분석 흐름 분리

AI 입력부터 결과 활용까지

① 입력 구성DB의 GitHub 기여 활동, 최근 학습 기록, 스킬·로드맵을 요약
② 분석 요청입력에 근거한 강점·역량 갭·다음 행동을 한국어로 요청
③ 결과 처리JSON 응답 형식 지정 → Java 결과 객체로 파싱 → Job에 저장
④ 결과 확인Job ID로 상태·결과 조회; 추천을 학습 방향 판단에 활용

기여 활동·학습 기록은 오늘부터 90일 전까지 조회합니다. 학습 기록은 날짜·제목·연결 스킬을 사용하며, 저장소 소스 코드·README나 학습 본문·시간은 분석 입력에 포함하지 않습니다. 결과는 등록된 데이터에 기반한 조언이며, 실제 역량을 객관적으로 측정한 점수는 아닙니다.

커리어 분석: 비동기 Job으로 결과 저장·조회 · 로드맵 초안: 별도 동기 API로 생성 결과 반환, 자동 저장하지 않음
03

핵심 문제 해결과 검증

01 · 동시 요청의 중복 Job 생성 방지
  • 문제. 조회 후 저장만 하면 동시 요청이 모두 기존 작업이 없다고 판단할 수 있었습니다.
  • 해결. DB UNIQUE 제약을 최종 기준으로 두고, 생성에 성공한 요청만 실행합니다. 생성은 독립된 트랜잭션(REQUIRES_NEW)으로 분리해 중복 INSERT 실패 후 기존 Job을 조회하도록 했습니다.
  • 검증. Testcontainers의 MySQL·Redis 환경에서 동일 사용자·키로 Service를 10개 스레드에서 호출하고, 모두 성공하며 같은 Job ID를 반환하는지 확인했습니다.
02 · AI 입력 구성 중 지연 로딩 오류
  • 문제. 비동기 분석에서 학습 기록의 스킬 등 연관 데이터를 읽을 때 LazyInitializationException이 발생했습니다.
  • 해결. 필요한 스킬·카테고리를 Repository의 Fetch Join으로 함께 조회해, AI 입력 구성 시 추가 지연 로딩에 의존하지 않도록 했습니다.
  • 검증. 연관 데이터가 있는 통합 테스트를 구성하고 학습 기록의 스킬, 스킬의 카테고리, 로드맵 단계의 스킬이 AI 입력에 포함되는지 확인했습니다.
03 · 외부 장애 정책의 실제 동작 확인
  • 설계. GitHub 페이지 조회를 별도 Bean으로 분리해 재시도·Circuit Breaker가 Spring 프록시를 통해 적용되도록 했습니다.
  • 개선. 로드맵 초안의 직접 구현 재시도를 다른 Gemini 호출과 같은 오류 분류 정책으로 통일했습니다.
  • 검증. 실제 Gemini 클라이언트의 연결 실패로 Circuit Breaker OPEN 전환을 확인하고, 별도 MockWebServer 테스트에서 초안 호출의 503은 최대 2회, 400·429는 1회 요청 후 실패하는지 검증했습니다.
04 · 재배포 후 세션 유지 방식 개선
  • 문제. Redis까지 재생성하는 배포 경로를 확인하니 세션 보존이 이미지의 익명 볼륨과 RDB 복구에 의존하고 있었습니다.
  • 해결. named volume·AOF를 명시하고, 메모리 확보를 위한 세션 제거를 막도록 noeviction을 적용했습니다. 배포는 백엔드만 교체하도록 변경했습니다.
  • 검증. 운영 서버에서 백엔드 재배포와 Redis 재시작 후 기존 로그인이 유지됨을 확인했습니다. noeviction은 메모리 부족 시 새 쓰기가 실패할 수 있어 용량 관리가 필요합니다.
04

배포·성능 검증

CI/CD와 운영
  • PR에서 GitHub Actions로 Gradle 빌드·테스트를 실행하고, main 반영 시 Docker 이미지를 빌드해 GHCR에 게시
  • EC2는 이미지를 받아 Docker Compose로 백엔드만 교체해 운영 서버의 빌드 부담 분리
  • CloudFront에서 화면과 API를 같은 도메인으로 제공해 Mixed Content·교차 사이트 쿠키 문제 해결
  • 단일 백엔드 교체 중 수 초간 502가 발생하므로 무중단 배포와는 구분
측정 범위
  • 대상 API: /api/skills, /api/study-logs
  • 실험 1: ASG 백엔드 1대에서 JVM·컨테이너 메모리 조정 전후의 100 VU 결과 비교
  • 실험 2: 조정 후 백엔드 1대·3대에 800 VU 부하를 주고 지연 시간과 처리량 비교
  • 관측: 컨테이너 상태·메모리와 Prometheus·Grafana 지표 확인

컨테이너 재시작 조사와 메모리 설정 개선

부하 중 컨테이너 재시작이 발생해 헬스체크 설정, 종료 상태, 메모리 사용량과 JVM 설정을 순서대로 확인했습니다. 헬스체크 완화 후에도 재현되어 해당 설정만으로는 설명하기 어렵다고 판단했습니다.

관측OOMKilled=false, ExitCode=0
유휴 메모리 389MB / 400MB
판단메모리가 한도에 근접해 힙 외 영역까지 고려한 설정 조정 필요
조치JVM 영역별 상한 명시
컨테이너 한도 400MB → 550MB
재측정같은 k6 시나리오에서 재시작과 부하 오류가 사라짐을 확인
-Xmx170m -XX:ReservedCodeCacheSize=48m -XX:MaxMetaspaceSize=150m

종료 상태와 JVM 예약 상한만으로 메모리 부족을 직접 입증한 것은 아닙니다. 영역별 실제 사용량은 측정하지 않았고 JVM 설정과 컨테이너 한도를 함께 변경했으므로, 특정 영역을 단일 원인으로 확정하거나 두 조치의 효과를 분리하지 않았습니다. 이 설정은 확장 실험 환경에 적용한 값입니다.

스킬·학습 기록 조회 API를 같은 k6 스크립트로 측정한 결과입니다. 800 VU는 가상 사용자 수이며 실제 사용자 수나 초당 요청 수와 같지 않습니다. JVM 설정과 컨테이너 한도를 함께 조정했으며 상시 운영 서버와는 구성이 다릅니다. 확장 실험은 DB·Redis를 기존 EC2에 공유한 조건으로 수행했고, ALB·ASG는 실험 후 제거했습니다. AI 분석 처리량이나 DB·Redis 이중화를 검증한 결과는 아닙니다.

05

설계에서 배운 점

트랜잭션과 실행 순서를 함께 설계

외부 API 대기와 DB 저장을 분리하고, 분석 작업은 커밋한 뒤 실행하도록 구성했습니다. 동일 키의 중복 생성은 애플리케이션의 사전 조회만 믿지 않고 DB 제약으로 제어했습니다.

테스트는 실제 호출 경로와 데이터를 반영

재시도·Circuit Breaker 같은 AOP 기능은 프록시를 거치는 호출 경로에서 확인해야 합니다. 연관 데이터가 없는 테스트만으로는 지연 로딩 오류를 발견하기 어려워, 실제로 사용하는 관계가 채워진 데이터를 구성했습니다.

관측 사실과 원인 추정을 구분

메모리 설정 조정 후 부하 오류가 사라진 것은 확인했지만 조치별 효과는 분리하지 못했습니다. 백엔드 3대의 처리량도 1대의 약 1.52배였으며, 증가 폭을 제한한 원인은 확정하지 않았습니다. 다음 실험에서는 DB 지표와 JVM 영역별 메모리를 함께 기록할 계획입니다.

현재 한계와 다음 과제

Job 큐는 서버 메모리에 있어 재시작 시 대기·실행 작업을 자동 복구하지 못합니다. 재시작 후 남은 작업을 식별하고 실패 처리하거나 재실행하는 정책이 필요합니다. DB·Redis도 단일 EC2에 있어 전체 서버 장애에 대비한 이중화는 구현하지 않았습니다.
