01

프로젝트 요약

배경. GitHub 활동과 학습 기록, 보유 기술 및 로드맵이 흩어져 있어 성장 현황과 다음 학습 방향을 함께 보기 어려웠습니다. 이를 하나의 서비스로 모아 목표와 현재 활동을 비교하고 AI 분석 결과를 제공하고자 했습니다.

구현. GitHub OAuth 로그인과 활동 동기화, Skill·StudyLog·Roadmap 관리 API를 만들고 분석 요청은 비동기 Job으로 처리합니다. MySQL·Redis 기반 백엔드를 AWS에 배포하고 CI/CD 및 부하테스트로 운영 특성을 확인했습니다.

현재 운영 구성입니다. ALB·ASG는 아래의 일회성 부하테스트에서만 사용했습니다.

API·인증
  • GitHub OAuth2 로그인과 Spring Security 메서드 권한 검사로 본인 API와 관리자 API 분리
  • GitHub 활동 동기화와 Skill·StudyLog·Roadmap 관리 API 제공
  • 로그인 세션을 Redis에 저장해 백엔드 컨테이너 재배포 후에도 유지
데이터·트랜잭션
  • JPA 엔티티와 Request/Response DTO를 분리하고 MySQL 스키마를 Flyway로 관리
  • GitHub 외부 호출 후 별도 Writer에서 저장해 외부 API 응답을 기다리는 동안 DB 트랜잭션을 유지하지 않음
  • 연관 데이터 로딩 오류를 Fetch Join과 실제 데이터 통합 테스트로 해결
외부 연동·안정성
  • GitHub REST·GraphQL을 함께 연동하고 Gemini 호출에 타임아웃·재시도·Circuit Breaker 적용
  • Gemini 동시 호출을 Bulkhead로 제한하고 재시도가 적절하지 않은 4xx는 제외
  • AI 클라이언트를 인터페이스로 분리해 공급사 의존성을 격리
비동기 분석
  • 요청 접수 시 Job ID를 즉시 반환하고 별도 실행기에서 분석
  • Job 상태와 결과를 조회 API로 제공하며, 동일 사용자·요청 키의 중복 실행을 DB UNIQUE 제약으로 방지

핵심 데이터 흐름

① 활동 수집GitHub REST·GraphQL 조회
② 데이터 저장MySQL의 GitHub 활동·Skill·StudyLog·Roadmap
③ 분석 요청Job 생성 · 202 Accepted · ID 반환
④ 결과 조회Gemini 분석 후 상태·결과 GET
Job 상태: PENDING → RUNNING → COMPLETED / FAILED · 동일 키 재요청: 기존 Job ID 반환

개념 흐름도입니다. 실제 테이블 관계와 컬럼을 확정한 ERD는 코드의 엔티티·Flyway 정의를 검증한 뒤 추가하는 것이 정확합니다.

03

핵심 문제 해결과 검증

01 · 외부 API와 DB 저장 경계
  • 문제. GitHub 호출을 저장 트랜잭션 안에서 처리하면 외부 응답 지연만큼 트랜잭션이 길어짐
  • 해결. 외부 조회와 저장을 분리하고 GithubSyncWriter를 별도 Bean으로 구성
  • 검증. 실제 연관 데이터를 사용해 지연 로딩 오류를 재현하고 Fetch Join으로 수정
02 · 분석 Job의 중복 실행 방지
  • 문제. 조회 후 INSERT만으로는 동시 요청에서 중복 Job을 막을 수 없음
  • 해결. (user_id, idempotency_key) UNIQUE 제약과 독립 생성 트랜잭션 적용
  • 검증. 실제 MySQL·Redis에서 동일 키 10개 동시 요청 시 레코드 1개 생성 확인
03 · 외부 서비스 장애 대응
  • GitHub·Gemini 호출의 타임아웃, 제한적 재시도, Circuit Breaker 적용
  • Gemini 동시 호출은 Bulkhead로 제한하고 AOP self-invocation 구간은 별도 Bean으로 분리
  • AI 호출 실패 시 Job의 FAILED 상태를 통합 테스트로 확인
04

배포·성능 검증

CI/CD와 운영
  • PR 빌드 검사 후 main 반영 시 GitHub Actions에서 빌드·테스트·GHCR 이미지 게시
  • EC2가 이미지를 받아 Docker Compose로 재기동해 서버 내 Gradle 빌드 부담 제거
  • Spring Session Redis 적용 후 컨테이너 재생성 시 로그인 유지 확인
측정과 분석
  • k6로 DB 조회 API(/api/skills, /api/study-logs)를 800 VU에서 측정
  • 단일 t3.micro의 p95 1.24초 구간에서 SQL·CPU·풀 사용을 확인하고 CPU 병목으로 판단
  • Actuator·Micrometer·Prometheus·Grafana로 HTTP·JVM·DB·Job 지표 관찰

800 VU 부하테스트 비교

p95 응답 시간 · 낮을수록 좋음단일 t3.micro — 1,240ms
ALB + ASG 백엔드 3대 — 176.48ms
처리량 · 높을수록 좋음단일 환경 — 약 166.6 req/s*
ALB + ASG 3대 — 599.6 req/s

* 단일 환경 처리량은 기록의 ‘3.6배 증가’와 599.6 req/s에서 역산한 근삿값입니다. 단일 환경 오류율 0.02%, 확장 실험 오류율 1.10%. 인프라 구성이 함께 달라진 비교이며, ALB·ASG는 실험 후 제거했습니다. ASG 1대에서 관찰한 오류·재시작의 근본 원인은 조사 중입니다.

05

설계에서 배운 점
