AIPF — 보기·납기 입력 자동화

정식 프로젝트명 — 신한라이프 생성형AI 활용한 PF시스템 내 보기·납기 입력 자동화(AIPF) 구축. 보험 기초서류에서 보기·납기 정보를 생성형 AI로 추출해 PF 시스템에 반영하는 과정을 자동화한 프로젝트로, 저는 문서 구조화(Parser)를 솔루션 위에 커스텀 개발하고, 구조화부터 정보 추출·필터링·DB 적재까지 잇는 비동기 백엔드 파이프라인을 설계·구현했습니다.

01

프로젝트 요약

배경. 기존 보기납기 업무는 작업자가 MCP에서 기초서류를 직접 색인하고 문서를 확인해 보기납기 정보를 수기로 입력한 뒤 PF 시스템에 반영하는 방식으로 운영되었습니다. 상품 출시 전 문서가 반복적으로 수정되면서 기존 작업을 재수행해야 했고, 그 결과 최대 35일의 업무 기간과 휴먼 에러 가능성이 함께 발생했습니다.

AIPF는 이 입력 과정을 문서 구조화 → 생성형 정보 추출 → 코드 매핑·필터링으로 이어지는 파이프라인으로 자동화하는 프로젝트입니다. 정보 추출 로직은 데이터분석가 팀이 담당했고, 저는 솔루션 파서에 커스텀 확장을 추가해 문서 구조화를 개발하고, 구조화 결과를 추출·필터링·DB 적재로 잇는 백엔드를 맡았습니다.
제 영역에서 풀어야 했던 문제는 네 가지였습니다. 형식이 제각각인 문서의 병합 셀·중첩 표·취소선을 후속 단계가 쓸 수 있는 일관된 구조로 바꾸는 것, LLM 추론처럼 오래 걸리는 처리가 API 요청을 막지 않게 하는 것, 여러 Worker가 병렬로 처리한 문서들의 완료 시점을 판단해 다음 단계 호출이 중복되지 않게 하는 것, 그리고 문서가 수시로 개정되는 환경에서 실패하거나 바뀐 부분만 안전하게 다시 처리하는 것입니다.

02

프로젝트 구조 · 아키텍처

문서 구조화(Parser), 정보 추출(Extract), 코드매핑·필터링(Filtering)은 각각 독립된 컨테이너로 동작합니다. 서비스 사이는 HTTP API로 트리거하고, 서비스 내부는 Celery Queue/Worker로 처리해, 장시간 작업이 API를 막지 않고 단계별로 독립적으로 조절·배포할 수 있게 설계했습니다.

설계 원칙 01 — 서비스 경계는 HTTP, 서비스 내부는 Queue

초기에는 추출·필터링이 API 핸들러 안에서 동기로 실행되었고, 추출 Worker가 필터링 Queue에 작업을 직접 넣는 구조였습니다. API는 작업만 접수하고 즉시 응답하도록 바꾸고, 서비스 간은 API 계약만 공유하도록 HTTP로 연결했습니다. 한 서비스의 내부 구현이 바뀌어도 다른 서비스를 고칠 필요가 없고, 단계별 Worker 수를 따로 조절할 수 있습니다. 실제로 LLM 호출이 몰리는 Extract는 Worker concurrency를 6으로, Parser와 Filtering은 각 2로 차등 구성했습니다.

설계 원칙 02 — 판정은 DB, 실행 권한은 Redis

배치 완료 여부는 DB에서 잔여 대기 문서 수로 판정하고, 잔여 문서가 0일 때 Redis HSETNX로 동시에 완료한 워커 중 한 워커만 Filtering API 호출 권한을 얻도록 했습니다.

설계 원칙 03 — 다시 실행해도 안전한 최소 단위로 재처리

단계별 중간 결과와 처리 상태를 남기고, 재처리는 문서 또는 대표보종명 단위로 한정했습니다. Filtering 부분 재실행 시에는 해당 범위의 기존 데이터를 지우고 다시 적재해 결과가 중복 적재되지 않게 했습니다.

03

문제 해결

파이프라인을 운영 가능한 수준으로 만드는 과정에서 마주한 핵심 이슈와 해결 과정입니다. 결과 칸에서 “기대 효과”로 표시한 항목은 구조 변경으로 의도한 효과이며, 운영 로그로 별도 검증하지는 못한 내용입니다.

Parser

문서마다 다른 표 구조 — 솔루션 파서 위에 커스텀 구조화 개발

이슈 · 원인

솔루션 파서가 주는 결과는 문단·표 요소의 나열이라, 어떤 표가 어떤 섹션에 속하는지 알 수 없었습니다. 또 문서마다 병합 셀과 표 안의 표(중첩 표)가 많고, 선언된 행/열 수와 실제 HTML 태그 수가 어긋나는 경우가 있었으며, 개정 이력인 취소선 내용까지 섞여 있어 그대로는 정보 추출에 쓸 수 없었습니다.

해결 과정
  • 솔루션의 커스텀 확장(훅)에 구조화 로직을 추가 개발 — 제목 패턴과 표 등장 위치로 본문을 섹션·문단 트리로 재구성
  • 병합 범위를 2차원 그리드에 복제하고, 행/열 수 불일치를 실제 태그 기준으로 보정, 중첩 표는 재귀적으로 파싱
  • 취소선 구간을 제거하고, 취소로 비게 된 행은 삭제해 현행 내용만 남김
  • 문서명·필수 대제목이 없으면 파싱 실패로 기록하고, 이전 버전과 비교한 변경점(diff) 파일 생성
결과
  • 사업방법서·판매예규·별첨을 하나의 일관된 JSON 구조로 산출해 후속 추출 단계의 입력 형식 통일
  • 구조가 깨진 문서는 추출 전에 걸러내 LLM 호출 낭비와 잘못된 결과 전파 방지
Extract → Filtering

동시에 끝난 여러 Worker 중 한 Worker만 다음 단계를 호출 — Barrier 동기화

이슈 · 원인

필터링은 한 배치의 문서들을 서로 비교하는 작업이라, DB상 잔여 대기 문서가 0이 된 시점에 한 번만 호출되어야 했습니다. 초기에는 Redis 카운터로 완료 건수를 셌는데, Celery 자동 재시도로 같은 문서가 두 번 집계될 수 있었고, 트리거 여부를 읽은 뒤 쓰는 사이에 다른 Worker가 끼어드는 경쟁 조건도 있었습니다.

해결 과정
  • 완료 판정 기준을 Redis 카운터에서 DB 문서 상태로 이동 — Worker는 자기 문서 상태를 갱신한 뒤 잔여 문서 수를 조회
  • 잔여 문서가 0이면 Redis HSETNX로 트리거 플래그 설정을 시도해, 설정에 성공한 한 Worker만 필터링 API 호출 권한을 획득
  • 완료 처리를 finally 블록에 두어 실패 문서도 실패 상태로 기록된 뒤 집계되도록 구성
결과
  • 재시도로 인한 중복 집계를 막고, 여러 Worker가 동시에 완료해도 Filtering API 호출 권한은 한 Worker만 획득
  • 일부 문서가 실패해도 배치 전체가 다음 단계로 넘어가지 못하고 멈추는 상황 방지
API

장시간 처리 중 Gunicorn WORKER TIMEOUT — 요청 흐름에서 처리 분리

이슈 · 원인

매칭 처리 중 Gunicorn WORKER TIMEOUT과 함께 워커가 강제 종료되었습니다. 처리 시간 초과와 컨테이너 메모리 부족을 원인 후보로 놓고 코드 구조를 대조한 결과, async 핸들러 안에서 동기 pandas 연산이 길게 실행되며 이벤트 루프가 막히고, 그로 인해 워커 생존 신호가 끊기는 구조를 1순위 원인으로 좁혔습니다.

해결 과정
  • docker stats로 메모리·CPU를 관찰해 메모리 원인과 시간 원인을 구분하는 검증 방법 수립
  • 반복 DataFrame 연산, 후보 조합 생성량, 결과 누적량 등 처리 함수 내부의 부하 지점 식별
  • 처리를 API 핸들러에서 Celery Worker로 옮기고, API는 작업 접수 후 즉시 응답하도록 변경
결과
  • API는 처리 시간과 무관하게 작업 접수 후 즉시 응답하는 구조로 변경
  • 장시간 처리가 HTTP 요청 수명과 분리되어, 요청이 처리 완료를 기다리다 타임아웃되는 구조 해소
DB

다건 결과 적재의 긴 처리 시간 — 행 단위 호출에서 배치 요청으로

이슈 · 원인

결과를 DB에 적재할 때 행마다 SQL 프록시 API로 HTTP 요청을 보내 호출 횟수가 행 수만큼 늘었고, 다건 적재에 걸리는 시간과 트랜잭션이 길어졌습니다.

해결 과정
  • 1차: HTTP 클라이언트를 공유하고 스레드 풀로 행 단위 호출을 병렬화 — 연결 비용은 줄었지만 호출 횟수는 그대로
  • 2차: 결과를 1000행 단위로 묶어 SQL 프록시의 배치 적재(insertBatch) 요청 1회로 전송하도록 전환
  • 연결 수 제한을 둔 HTTP 클라이언트를 재사용해 프록시 서버 부하 통제
결과
  • 적재 요청 수를 행 수 기준에서 1000행당 1회로 축소
  • 요청 하나가 처리하는 범위를 청크 단위로 제한해 적재 시간과 트랜잭션 부담 완화
전체

일부 문서 실패와 잦은 문서 개정 — 실패 구간만 안전하게 재처리

이슈 · 원인

일부 문서만 실패해도 배치 전체를 다시 돌리면 이미 끝난 파싱과 비용이 큰 LLM 추론까지 반복하게 됩니다. 또 재실행 시 이미 적재된 결과 위에 같은 데이터가 중복으로 쌓일 위험이 있었습니다.

해결 과정
  • 단계별 재처리 단위 정의 — 파싱은 오류 시 플래그 파일로 1회만 자동 재요청, 추출은 문서 1건 = Celery 태스크 1개로 실패 문서만 자동 재시도, 필터링은 사용자가 재매핑한 대표보종명만 부분 재실행
  • 버전별 중간 결과 파일과 문서·단계별 처리 상태를 남겨, 재실행 시 성공한 단계의 결과를 재사용
  • 필터링 부분 재실행 시 해당 범위의 기존 DB 데이터를 삭제한 뒤 다시 적재해 멱등성 확보
결과
  • 재처리 범위를 실패·수정 구간으로 한정해 성공한 파싱·LLM 추론 결과를 재사용
  • 필터링을 여러 번 재실행해도 결과가 중복 적재되지 않는 구조 확보

01

문서 구조화부터 DB 적재까지 이어지는 비동기 파이프라인 구축

솔루션 위에 커스텀 개발한 문서 구조화부터 정보 추출, 코드매핑·필터링, 결과 DB 적재까지를 서비스 간 API와 단계별 Queue/Worker로 연결했습니다. 자동 매칭의 신뢰도가 낮은 결과는 사용자가 재매핑하고 해당 부분만 다시 처리하는 흐름도 함께 연결했습니다.

02

장시간 처리 분리로 API 안정성 확보

LLM 추론과 매칭 같은 장시간 처리를 Worker로 옮겨 HTTP 요청이 처리 완료를 기다리지 않도록 했고, 일부 문서의 실패가 배치 전체를 멈추지 않는 구조를 만들었습니다.

03

재시도가 일상인 환경을 전제로 한 설계

DB 상태 기반 완료 판정으로 재시도에 따른 중복 집계를, Redis HSETNX로 동시 완료 시 중복 호출을, Filtering 부분 재실행의 삭제 후 재적재로 중복 적재를 막도록 설계했습니다.

05

회고 · 배운 점

LLM을 파이프라인의 한 컴포넌트로 다룰 때는 호출 자체보다 그 앞뒤 — 처리 흐름의 분리, 완료 시점 판단, 실패와 재시도 처리 — 를 얼마나 견고하게 설계하느냐가 실제 운영 가능 여부를 좌우한다는 것을 이 프로젝트를 통해 확인했습니다.
배움 01

재시도가 있는 시스템에서는 "몇 번 실행됐는가"가 아니라 "지금 어떤 상태인가"로 판단해야 한다. Redis 카운터로 완료를 세다가 재시도 때문에 중복 집계되는 문제를 겪고, 판정 기준을 DB 상태로 옮기면서 멱등성의 의미를 체감했습니다.

배움 02

동시성 문제는 "확인하고 쓰기"를 한 동작으로 만드는 데서 풀린다. 확인과 기록 사이의 짧은 틈이 중복 실행을 만든다는 것을 겪고, 원자 연산 하나로 실행 권한을 확정하는 방식으로 해결했습니다.

배움 03

비동기 파이프라인의 신뢰성은 코드보다 상태 설계에서 나온다. 문서·단계별 처리 상태와 중간 결과를 명확히 남기니, 재처리 범위를 좁힐 수 있었고 장애 대응과 이슈 공유·커뮤니케이션도 훨씬 단순해졌습니다.
