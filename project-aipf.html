AIPF — 보기·납기 입력 자동화

정식 프로젝트명 — 신한라이프 생성형AI 활용한 PF시스템 내 보기·납기 입력 자동화(AIPF) 구축. 보험 상품 정보 관리의 핵심 업무를 AI 기반으로 자동화해, 상품 개발 업무의 속도와 정확도를 함께 개선했습니다.

01

프로젝트 요약

배경. 기존 보기납기 업무는 작업자가 MCP에서 기초서류를 직접 색인하고 문서를 확인해 보기납기 정보를 수기로 입력한 뒤 PF 시스템에 반영하는 방식으로 운영되었습니다. 상품 출시 전 문서가 반복적으로 수정되면서 기존 작업을 재수행해야 했고, 그 결과 최대 35일의 업무 기간과 휴먼 에러 가능성이 함께 발생했습니다.

AIPF는 이 입력 과정을 생성형 AI 기반 ETL 파이프라인으로 자동화해, 문서 구조화 → 정보 추출 → 코드 매핑까지 이어지는 흐름을 시스템화하는 것을 목표로 시작한 프로젝트입니다. 형식이 제각각인 문서에서 규칙 기반 추출이 어려웠던 점, MCP와 PF 간 코드 체계가 달라 결과를 연결하기 어려웠던 점, 문서가 수시로 개정되는 환경에서 최신본을 실시간·배치로 반영해야 했던 점, 대량 문서 처리 중 특정 단계 지연이 전체 파이프라인에 영향을 주는 구조적 문제까지 함께 풀어야 했습니다.

02

프로젝트 구조 · 아키텍처

시스템은 MCP 연동 → 문서 구조화(Parser) → 생성형 정보 추출(Extract) → 코드매핑·조건필터링(Filtering)의 4단계로 구성됩니다. 처리 안정성을 위해 세 단계를 하나의 흐름으로 묶지 않고, 단계마다 독립된 Queue/Worker로 분리했습니다.

설계 원칙 01 — 단계별 Queue/Worker 분리

Parser → Extract → Filtering을 하나의 동기 흐름으로 묶지 않고 단계마다 독립된 Queue/Worker로 분리했습니다. 특정 단계가 지연되거나 실패해도 전체 파이프라인으로 전파되지 않고, 병렬 Worker 구조로 대량 문서를 처리할 수 있습니다.

설계 원칙 02 — 상태 기반 재처리

Redis 기반으로 문서 단위 처리 상태(성공·실패·대기)를 관리해, 실패한 문서만 골라 재처리할 수 있는 구조를 만들었습니다. 문서가 수시로 개정되는 환경에서도 전체를 다시 돌리지 않고 필요한 부분만 다시 처리합니다.

03

트러블슈팅

파이프라인을 프로덕션 수준까지 끌어올리는 과정에서 마주한 핵심 이슈와 해결 과정입니다.

Extract

여러 Worker가 동시에 끝내도 다음 단계는 정확히 한 번만 — Barrier 동기화

이슈 · 원인

대량 문서를 여러 Worker가 병렬로 처리하는 비동기 환경에서, 마지막 문서가 끝났을 때만 다음 단계(Filtering)를 정확히 한 번 호출해야 하는 문제가 있었습니다. 비동기 구조 특성상 단계별 완료 시점을 판단하기 어려웠고, Redis 카운터만으로는 중복 호출 또는 누락 위험이 있었습니다.

해결 과정
  • 문서 처리 완료 시마다 남은 처리 건수(pending count)를 다시 조회해 이중 확인
  • 잔여 건수가 0일 때 Redis HSETNX 원자적 연산으로 트리거 권한을 단 하나의 Worker만 획득하도록 Barrier 동기화 로직 구현
  • 예외 발생 시 1회 재시도 후, 재시도도 실패하면 해당 건만 실패 상태로 기록
결과
  • 여러 Worker가 동시에 마지막 문서를 끝내도 다음 단계가 정확히 한 번만 호출됨을 보장
  • 특정 단계의 지연·실패가 전체 처리에 전이되지 않는 구조 확보로 운영 안정성 개선
Extract

LLM 응답의 형식 불안정성 — 이상 문자와 재현성

이슈 · 원인

프롬프트와 입력이 동일해도 LLM 추론 결과에 의도치 않은 한자(CJK) 혼입 등 예기치 않은 형식 오류가 발생해, 단순 호출만으로는 후속 파이프라인이 깨지는 문제가 있었습니다.

해결 과정
  • LLM inference 연동 시 temperature=0, seed=0으로 고정해 재현성 확보
  • CJK 이상 문자 등 도메인 특화 이상 패턴을 감지해 최대 3회 재시도하는 검증 로직 구현
  • 문서 단위 실패 건에는 LLM 재시도와 별개의 상위 재시도 레이어를 추가
결과
  • 형식이 불안정한 응답으로 인한 후속 단계 실패율 감소
  • 기초서류 구조화·속성 추출 정확도를 100%에 가까운 수준까지 끌어올리는 데 기여
Parser

문서마다 다른 표 구조 — 병합 셀과 중첩 표

이슈 · 원인

형식이 제각각인 문서마다 병합된 셀과 중첩 표가 많아, 기존 룰 기반 엔진과 단순 텍스트 추출로는 원하는 구조화 데이터를 얻기 어려웠습니다.

해결 과정
  • 제목 정규식과 표 등장 시점을 기준으로 본문을 섹션·문단 트리로 재구성하는 단일 패스 상태머신 구현
  • rowspan/colspan 병합 범위를 2차원 그리드에 복제하고, 선언된 행/열 수와 실제 태그 수 불일치를 보정
  • 문서 종류별 파일명 라우팅으로 서로 다른 파서·후처리 로직 적용
결과
  • 서로 다른 문서 유형을 하나의 파이프라인에서 안정적인 구조화 데이터로 산출
  • 표 병합·불일치 엣지케이스 처리로 후속 정보 추출 단계의 입력 품질 확보

Filtering

MCP·PF 코드 체계 불일치와 상품·보종 매칭 누락

이슈 · 원인

MCP와 PF 간 코드 체계가 달라 상품·보종 단위로 결과를 연결하기 어려웠고, 추출된 보종명·상품명도 약어·띄어쓰기·오탈자 등으로 표준 명칭과 정확히 일치하지 않는 경우가 많아 완전 일치 매칭으로는 누락이 많았습니다.

해결 과정
  • 완전 일치 대신 토큰 단위로 쪼갠 뒤 F1 스코어(정밀도·재현율의 조화평균)로 유사도 계산
  • F1 스코어가 기준 미달인 저신뢰 매칭만 별도로 분리해 담당자가 재확인하는 human-in-the-loop 프로세스 설계
  • 담당자가 재매핑하면 코드 매칭 단계는 건너뛰고 이후 필터링 단계만 부분 재실행
결과
  • 표기 차이가 있는 항목도 자동 매칭 커버리지에 포함시키면서 낮은 신뢰도 건은 사람이 검증하는 이중 안전장치 확보
  • 필터링 단계 단독 재실행으로 매핑 오류 수정 시 전체 파이프라인 재처리 비용 제거

전체

대량 문서 처리 중 일부 실패 — 상태 기반 재처리 구조

이슈 · 원인

대량 문서를 처리하는 과정에서 일부 문서만 실패해도 배치 전체를 다시 돌리면 이미 처리된 문서까지 중복 처리되어 비용이 컸고, 문서가 수시로 개정되는 환경에서는 최신 문서만 다시 반영할 방법이 필요했습니다.

해결 과정
  • Redis에 문서 단위 처리 상태(성공·실패·대기)를 기록하는 상태 관리 구조 설계
  • 실패 문서만 골라 해당 Queue에 재적재해 재처리하는 상태 기반 재처리 로직 구현
  • 단계별로 Queue/Worker를 분리해, 재처리가 다른 단계의 정상 처리 흐름에 영향을 주지 않도록 격리
결과
  • 실패 문서만 선택적으로 재처리해 불필요한 중복 처리 제거
  • 문서 1건당 약 10초 수준의 처리 속도를 병렬 Worker 구조로 안정적으로 유지

02

단계별 Queue/Worker 분리로 운영 안정성 확보

특정 단계의 지연·실패가 전체 처리에 전이되지 않는 구조를 확보해, 대량 문서를 처리하는 환경에서도 안정적으로 운영할 수 있게 되었습니다.

03

정확도와 운영 안정성을 함께 고려한 설계 적용

Redis 기반 Barrier 동기화, 상태 기반 재처리, F1 유사도 기반 매핑 + human-in-the-loop 등 각 단계에서 자동화 효율과 신뢰성의 균형을 맞췄습니다.

05

회고 · 배운 점

LLM을 파이프라인의 한 컴포넌트로 다룰 때는 호출 자체보다 그 앞뒤 — 입력 정규화, 출력 검증·재시도, 동시성 제어 — 를 얼마나 견고하게 설계하느냐가 실제 운영 가능 여부를 좌우한다는 것을 이 프로젝트를 통해 확인했습니다.
배움 01

LLM은 정확도가 아니라 재현성과 실패 처리로 신뢰를 얻는다. temperature/seed 고정, 이상 패턴 감지, 다층 재시도가 모델 성능보다 운영 안정성에 더 크게 기여했습니다.

배움 02

완전 자동화가 어려운 문제는 피하지 않고 경계를 긋는다. 표기 차이 매칭처럼 100% 자동화가 어려운 영역은, 임계값 기반으로 자동 처리와 사람의 개입을 나누는 human-in-the-loop 설계가 정확도를 희생하지 않으면서 자동화 효과를 얻는 현실적인 접근이라는 것을 체감했습니다.

배움 03

비동기 파이프라인의 신뢰성은 코드보다 상태 설계에서 나온다. 문서 단위 처리 상태를 명확히 관리하고 단계를 분리하니, 장애 대응뿐 아니라 이슈 공유·커뮤니케이션도 훨씬 단순해졌습니다.
