AIPF — 보기·납기 입력 자동화

정식 프로젝트명 — 신한라이프 생성형AI 활용한 PF시스템 내 보기·납기 입력 자동화(AIPF) 구축. 보험 기초서류에서 보기·납기 정보를 생성형 AI로 추출해 PF 시스템에 반영하는 과정을 자동화한 프로젝트로, 저는 문서 구조화(Parser)를 솔루션 위에 커스텀 개발하고, 구조화부터 정보 추출·필터링·DB 적재까지 잇는 비동기 백엔드 파이프라인을 설계·구현했습니다.

01

프로젝트 요약

배경. 기존 보기납기 업무는 작업자가 MCP에서 기초서류를 직접 색인하고 문서를 확인해 보기납기 정보를 수기로 입력한 뒤 PF 시스템에 반영하는 방식으로 운영되었습니다. 상품 출시 전 문서가 반복적으로 수정되면서 기존 작업을 재수행해야 했고, 그 결과 최대 35일의 업무 기간과 휴먼 에러 가능성이 함께 발생했습니다.

AIPF는 이 입력 과정을 문서 구조화 → 생성형 정보 추출 → 코드 매핑·필터링으로 이어지는 파이프라인으로 자동화하는 프로젝트입니다. 정보 추출·필터링의 업무 로직은 데이터분석가 팀이 담당했고, 저는 솔루션 파서에 커스텀 확장을 추가해 문서 구조화를 개발하고, 구조화 결과를 추출·필터링·DB 적재로 잇는 백엔드를 맡았습니다.
제 영역에서 풀어야 했던 문제는 네 가지였습니다. 형식이 제각각인 문서의 병합 셀·중첩 표·취소선을 후속 단계가 쓸 수 있는 일관된 구조로 바꾸는 것, LLM 추론처럼 오래 걸리는 처리가 API 요청을 막지 않게 하는 것, 여러 Worker가 병렬로 처리한 문서들의 완료 시점을 판단해 다음 단계 호출이 중복되지 않게 하는 것, 그리고 문서가 수시로 개정되는 환경에서 변경된 문서만 재추출하고 현업 재매핑 후에는 Filtering만 다시 실행하는 것입니다.

02

프로젝트 구조 · 아키텍처

문서 구조화(Parser), 정보 추출(Extract), 코드매핑·필터링(Filtering)은 각각 독립된 컨테이너로 동작합니다. 서비스 사이는 HTTP API로 트리거하고, 서비스 내부는 Celery Queue/Worker로 처리해, 장시간 작업이 API를 막지 않고 단계별로 독립적으로 조절·배포할 수 있게 설계했습니다.

설계 원칙 01 — 서비스 경계는 HTTP, 서비스 내부는 Queue

초기에는 추출·필터링이 API 핸들러 안에서 동기로 실행되었고, 추출 Worker가 필터링 Queue에 작업을 직접 넣는 구조였습니다. API는 작업만 접수하고 즉시 응답하도록 바꾸고, 서비스 간은 API 계약만 공유하도록 HTTP로 연결했습니다. Filtering 내부 함수·태스크 인자 대신 HTTP 요청 계약에 맞춰 연동해 서비스 내부 구현에 대한 의존을 줄이고, 단계별 동시 실행 수를 조절할 수 있도록 했습니다. 실제로 LLM 호출이 몰리는 Extract는 Worker concurrency를 6으로, Parser와 Filtering은 각 2로 차등 구성했습니다.

설계 원칙 02 — 판정은 DB, 실행 권한은 Redis

배치 완료 여부는 DB에서 잔여 대기 문서 수로 판정하고, 잔여 문서가 0일 때 Redis HSETNX로 동시에 완료한 워커 중 한 워커만 Filtering API 호출 권한을 얻도록 했습니다.

설계 원칙 03 — 변경과 재매핑에 맞춰 재실행 범위 제한

변경 없는 문서는 기존 추출 결과를 재사용하고, 현업 재매핑 후에는 갱신된 DB 정보로 해당 대표보종명 범위의 Filtering만 다시 수행합니다. 상세 흐름은 아래 재처리 사례에 정리했습니다.

03

문제 해결

문서 구조화, 장시간 작업 분리, 완료 판정, 결과 적재와 재처리를 개선한 과정입니다.

Parser

문서마다 다른 표 구조 — 솔루션 파서 위에 커스텀 구조화 개발

이슈 · 원인

솔루션 파서가 주는 결과는 문단·표 요소의 나열이라, 어떤 표가 어떤 섹션에 속하는지 알 수 없었습니다. 또 문서마다 병합 셀과 표 안의 표(중첩 표)가 많고, 선언된 행/열 수와 실제 HTML 태그 수가 어긋나는 경우가 있었으며, 개정 이력인 취소선 내용까지 섞여 있어 그대로는 정보 추출에 쓸 수 없었습니다.

해결 과정
  • 솔루션의 커스텀 확장(훅)에 구조화 로직을 추가 개발 — 제목 패턴과 표 등장 위치로 본문을 섹션·문단 트리로 재구성
  • 병합 범위를 2차원 그리드에 복제하고, 행/열 수 불일치를 실제 태그 기준으로 보정, 중첩 표는 재귀적으로 파싱
  • 취소선 구간을 제거하고, 취소로 비게 된 행은 삭제해 현행 내용만 남김
  • 문서명·필수 대제목이 없으면 파싱 실패로 기록하고, 이전 버전과 비교한 변경점(diff) 파일 생성
결과
  • 사업방법서·판매예규·별첨을 하나의 일관된 JSON 구조로 산출해 후속 추출 단계의 입력 형식 통일
  • 구조가 깨진 문서는 추출 전에 걸러내 LLM 호출 낭비와 잘못된 결과 전파 방지
Extract → Filtering

동시에 끝난 여러 Worker 중 한 Worker만 다음 단계를 호출 — Barrier 동기화

이슈 · 원인

Filtering은 배치의 추출 결과를 함께 사용합니다. 초기에는 Redis 완료 카운터를 사용했지만, 성공·실패 시마다 카운터가 증가해 동일 문서의 재시도가 중복 집계될 수 있었습니다. 이 경우 실제 처리 완료 전에 후속 단계가 시작될 가능성이 있었습니다.

해결 과정
  • 완료 판정 기준을 Redis 카운터에서 DB 문서 상태로 이동 — Worker는 자기 문서 상태를 갱신한 뒤 잔여 문서 수를 조회
  • 잔여 문서가 0이면 Redis HSETNX로 트리거 플래그 설정을 시도해, 설정에 성공한 한 Worker만 필터링 API 호출 권한을 획득
  • 재시도 대기와 최종 실패를 DB 상태로 구분하고, 미완료 문서가 없을 때 후속 호출 조건 충족
결과
  • 재시도로 인한 중복 집계를 막고, 여러 Worker가 동시에 완료해도 Filtering API 호출 권한은 한 Worker만 획득
  • 일부 문서의 최종 추출 실패에도 Filtering을 진행하고, 추출 결과가 없는 문서를 경고로 안내하는 정책을 제안해 고객사와 합의
API · 병렬 처리

장시간 작업을 요청에서 분리하고 문서 단위 병렬 처리 적용

이슈 · 원인

추출·필터링을 API 핸들러에서 실행하면 LLM 추론과 매칭이 끝날 때까지 HTTP 요청이 유지됩니다. 문서가 여러 건일 때는 처리량을 늘릴 수 있는 실행 구조도 필요했습니다.

해결 과정
  • Extract·Filtering 실행을 Celery Queue/Worker로 분리하고 API는 큐 등록 후 응답하도록 변경
  • Extract를 문서 단위 태스크로 구성하고 동시 실행 수를 1에서 6으로 확대
  • 문서·단계별 처리 상태와 중간 결과를 별도로 저장해 접수 이후의 진행 확인과 재처리에 활용
결과
  • HTTP 요청이 LLM 추론·필터링 완료를 기다리지 않는 구조로 변경
  • 동시 실행 수 확대 전후 문서 50건 테스트에서 처리시간 약 7~8분 → 약 2분 확인
DB

다건 결과 적재의 긴 처리 시간 — 행 단위 호출에서 배치 요청으로

이슈 · 원인

결과를 DB에 적재할 때 행마다 SQL 프록시 API로 HTTP 요청을 보내 호출 횟수가 행 수만큼 늘었고, 반복 HTTP 호출이 다건 적재 지연의 원인이 되었습니다.

해결 과정
  • 1차: HTTP 클라이언트를 공유하고 스레드 풀로 행 단위 호출을 병렬화 — 연결 비용은 줄었지만 호출 횟수는 그대로
  • 2차: 결과를 1000행 단위로 묶어 SQL 프록시의 배치 적재(insertBatch) 요청 1회로 전송하도록 전환
  • HTTP 클라이언트를 재사용하고 최대 1,000행씩 청크 단위로 순차 전송
결과
  • 적재 요청 수를 행 수 기준에서 1000행당 1회로 축소
  • 1,000행 기준 HTTP 요청 1,000회 → 1회(99.9% 감소), 청크 단위로 요청당 데이터 크기 제한
전체

문서 개정과 현업 재매핑 — 기존 추출 결과를 활용한 부분 재실행

이슈 · 원인

일부 문서만 실패해도 배치 전체를 다시 돌리면 이미 끝난 파싱과 비용이 큰 LLM 추론까지 반복하게 됩니다. 또 재실행 시 이미 적재된 결과 위에 같은 데이터가 중복으로 쌓일 위험이 있었습니다.

해결 과정
  • 추출 실패는 문서 단위로 자동 재시도. 문서 재업로드 시 diff로 변경 여부를 판단해 변경 없는 문서는 기존 추출 결과 재사용
  • 변경된 문서는 전체 섹션을 Extract로 전달. 현업이 화면에서 재매핑 후 재실행하면 매핑 정보 DB 업데이트 API를 호출하고 갱신된 정보로 Filtering만 수행
  • Filtering은 대표보종명 등 대상 조건에 해당하는 기존 데이터를 삭제한 뒤 다시 적재해 결과가 누적되지 않도록 처리
결과
  • 변경 없는 문서와 현업 재매핑 건은 기존 추출 결과를 활용해 불필요한 LLM 재추출을 줄임
  • 현업이 확인·수정한 매핑을 후속 결과에 반영하는 부분 재실행 흐름 연결

회고 · 배운 점

LLM을 파이프라인의 한 컴포넌트로 다룰 때는 호출 자체보다 그 앞뒤 — 처리 흐름의 분리, 완료 시점 판단, 실패와 재시도 처리 — 를 얼마나 견고하게 설계하느냐가 실제 운영 가능 여부를 좌우한다는 것을 이 프로젝트를 통해 확인했습니다.
배움 01

재시도가 있는 시스템에서는 "몇 번 실행됐는가"가 아니라 "지금 어떤 상태인가"로 판단해야 한다. 동일 문서의 재시도가 카운터에 중복 반영될 수 있어, 실행 횟수 대신 DB의 문서별 상태를 완료 판정 기준으로 삼았습니다.

배움 02

완료 조건 판단과 호출 권한 제어는 별개의 책임이다. DB로 미완료 문서를 확인하고 Redis 원자 연산으로 호출권을 제어하면서, 상태 판단과 동시성 제어를 나눠 설계하는 방법을 배웠습니다.

배움 03

실패 시 현업이 어떻게 업무를 이어갈지도 설계해야 한다. 추출 실패 문서를 경고로 안내하는 정책을 고객사와 합의하고, 현업이 매핑을 수정한 뒤 Filtering만 다시 실행하는 흐름으로 연결했습니다.
