01

프로젝트 요약

BACKGROUND

A부서(실시간 심사 문서 처리)와 B부서(과거 축적 문서 일괄 처리), 두 부서를 대상으로 AgileSoda AIOCR 엔진을 실제 업무 시스템에 연동하는 중간 API 서버 2종을 설계·구현했다. OCR 엔진 자체를 개발한 것이 아니라, 문서별 분류·추출 스키마(JSON) 작성부터 API 연동, 결과 가공, 배치 운영까지 문서 처리 파이프라인 전 구간을 담당했다.

담당 업무 (부서별)

A부서 · 실시간 연동

수기로 입력하던 심사 항목을 AIOCR로 자동 추출·기입하는 구조로 전환. 실시간 REST API 설계, Nexacro 연동 대응, 이력 관리를 담당했다.

B부서 · 배치 연동

과거 축적 문서를 일괄 OCR 처리해 학습용 raw 데이터로 적재. 분석 트리거·콜백 API, 결과 CSV 변환, 배치 스크립트, crontab 스케줄을 담당했다.

A부서 — 실시간 연동 구조

SYNC-LIKE POLLING
  • AIOCR솔루션은 내부적으로 비동기(콜백 기반)로 동작하지만, 콜백 수신 전까지 처리 상태를 폴링하며 대기하는 구조로 클라이언트에는 동기 응답처럼 제공
  • 요청 단위로 중복 여부와 처리 상태를 관리하고, 완료 후 결과를 재조회할 수 있는 API를 함께 구현
  • Nexacro 프론트엔드 연동을 위한 Multipart 업로드 호환 처리 (표준 파라미터 바인딩 대신 요청 객체에서 파일을 직접 순회)
  • MyBatis / MySQL 기반 이력 관리

B부서 — 배치 연동 구조

FIRE-AND-FORGET
  • 실시간 응답이 필요하지 않은 대신 대량 문서를 반복 처리해야 했기에 배치 스크립트 기반의 완전 비동기 구조로 설계
  • 문서를 일정 건수 단위로 그룹핑해 순차 트리거, 그룹 간 대기 시간을 두어 처리 누적 예방
  • 처리 / 강제 종료·재기동 / 결과 전송을 별도 스크립트로 분리하고, 평일 주간의 실시간 사용자를 피해 crontab 스케줄을 평일(야간)·주말(주·야간)로 구분해 운영
  • 가공 결과를 CSV로 변환·유형별 분류 후 내부 서버로 전송하는 파이프라인까지 연결
03

문제 해결

A부서

AIOCR솔루션의 비동기 콜백 구조 때문에, 실시간성이 필요한 화면에서 즉시 응답이 불가능했다

원인

OCR 분석 결과가 콜백으로 비동기 전달되는 구조라, 요청-응답 한 사이클 안에서 결과를 바로 돌려줄 수 없었음

해결 과정

콜백 수신 전까지 처리 상태를 폴링하며 대기하는 구조를 구현하고, 요청 단위 중복·상태 관리와 재조회 API를 함께 설계

결과

클라이언트 입장에서는 동기 응답처럼 실시간 심사 화면에 결과를 반영할 수 있게 됨

B부서

대량 문서 그룹을 쉬지 않고 연속 호출하면 처리가 누적되어 오류로 이어질 위험이 있었다

원인

한 그룹에 문서가 많으면 OCR 처리 시간이 길어지는데, 이전 그룹 처리가 끝나기 전에 다음 그룹이 연속 호출되면 처리가 누적되어 오류가 날 수 있는 구조. 또한 평일 주간에는 실시간 사용자가 있어 배치에 쓸 수 있는 시간이 제한적이었음

해결 과정

문서를 일정 건수 단위로 그룹핑하고, 그룹 호출 사이에 대기 간격을 두도록 배치 스크립트를 직접 설계. 처리/종료·재기동/결과 전송을 스크립트로 분리하고, 실시간 사용 시간대를 피해 평일은 야간·주말은 주·야간으로 crontab 스케줄링. 엔진 Pod가 간헐적으로 비정상 상태가 되는 경우에 대비해 종료 시점에 Pod를 재기동

결과

처리 누적으로 인한 오류를 사전에 예방하는 구조로 배치를 운영하고, 실시간 사용 시간대와 겹치지 않도록 분리

A부서

Nexacro 프론트엔드에서 표준 Multipart 업로드가 정상 동작하지 않았다

원인

A부서가 사용하는 Nexacro 프론트엔드의 요청 방식이 표준적인 Spring Multipart 처리 방식과 호환되지 않음

해결 과정

표준 방식(@RequestParam MultipartFile[] 바인딩)이 Nexacro 요청에서 동작하지 않는 것을 확인하고, 요청 객체(MultipartHttpServletRequest)에서 파일을 직접 순회해 저장하도록 서버 업로드 처리 방식을 변경

결과

Nexacro 환경에서도 정상적으로 문서 업로드·연동이 가능해짐

    수기 입력 부담 절감. 담당자가 문서를 보며 직접 입력하던 심사 항목을 자동 추출·기입 구조로 전환해 반복적인 수작업 부담을 줄였다.

  • B부서

    모델 개발 데이터 기반 마련. 과거 문서를 자동 OCR 처리해 raw 데이터로 적재하는 구조를 구축, 이후 자체 모델 개발의 학습 데이터 기반을 마련했다.

05

회고 · 배운 점

DESIGN

같은 엔진, 다른 두 개의 설계

동일한 AIOCR 엔진을 연동하더라도, 부서의 업무 특성(실시간성 vs. 대량 처리)에 따라 완전히 다른 아키텍처가 필요하다는 것을 체감했다. 요구사항을 먼저 "동기적 사용자 경험이 필요한가"와 "처리량이 우선인가"로 구분해 접근한 것이 설계 방향을 잡는 데 핵심이었다.

ASYNC

비동기 콜백을 다루는 감각

외부 엔진의 비동기 콜백 구조를 그대로 노출하지 않고, 상태 폴링과 재조회 API로 감싸 클라이언트 경험을 단순하게 만드는 패턴을 익혔다.

OPERATIONS

운영까지 고려한 배치 설계

배치는 "돌아가는 것"과 "안정적으로 운영되는 것"이 다르다는 걸 배웠다. 처리/종료·재기동/전송 스크립트를 분리하고 crontab 스케줄을 요일별로 다르게 가져간 것은, 평일 주간의 실시간 사용자를 방해하지 않으면서 배치 처리 시간을 확보하기 위한 선택이었다. 엔진 Pod가 간헐적으로 비정상 상태가 되는 점도 운영에 포함해, 종료 시점에 재기동하도록 했다.
