BACKGROUND

A부서(실시간 심사 문서 처리)와 B부서(과거 축적 문서 일괄 처리), 두 부서를 대상으로 AgileSoda AIOCR 엔진을 실제 업무 시스템에 연동하는 중간 API 서버 2종을 설계·구현했다. 문서별 분류·추출 스키마(JSON), 분석 요청·콜백 수신 API, 결과 가공과 배치 운영을 담당했다.

A부서 — 실시간 연동 구조

SYNC-LIKE POLLING
  • 고객사는 하나의 API 요청에서 분석 결과까지 응답받아야 했으므로, 분석 요청 후 처리 상태를 폴링하고 콜백 결과가 반영되면 원래 요청에 결과를 반환
  • 요청 단위로 중복 여부와 처리 상태를 관리하고, 완료 후 결과를 재조회할 수 있는 API를 함께 구현
  • MyBatis / MySQL 기반 이력 관리

B부서 — 배치 연동 구조

BATCH + CALLBACK
  • 실시간 응답이 필요하지 않은 대신 대량 문서를 반복 처리해야 했기에 배치 요청과 콜백 결과 수신을 분리한 구조로 설계
  • 문서를 일정 건수 단위로 나눠 순차 요청, 그룹 간 고정 대기 시간을 두어 요청 누적 완화
  • 배치 실행 시간을 crontab으로 평일(야간)·주말(주·야간)로 구분해 운영
  • 가공 결과를 CSV로 변환·유형별 분류 후 내부 서버로 전송하는 파이프라인까지 연결
03

문제 해결

A부서

고객사의 동기 응답 요구와 OCR 엔진의 비동기 콜백 방식을 연결

원인

고객사는 요청의 응답으로 최종 결과를 요구했으나, 엔진은 요청 접수와 분석 결과 전달이 분리된 콜백 방식으로 동작

해결 과정

콜백 수신 전까지 처리 상태를 폴링하며 대기하는 구조를 구현하고, 요청 단위 중복·상태 관리와 재조회 API를 함께 설계

결과

고객사는 별도로 콜백을 처리하지 않고 기존 요청의 응답으로 분석 결과를 받을 수 있게 됨. 분석 완료까지 기다리는 구조이므로 즉시 응답이나 처리 속도 개선을 의미하지는 않음

B부서

대량 배치와 실시간 업무가 같은 OCR 자원을 사용

원인

한 그룹에 문서가 많으면 OCR 처리 시간이 길어지는데, 이전 그룹 처리가 끝나기 전에 다음 그룹이 연속 호출되면 처리가 누적되어 오류가 날 수 있는 구조. 또한 평일 주간에는 실시간 사용자가 있어 배치에 쓸 수 있는 시간이 제한적이었음

해결 과정

문서를 그룹으로 나눠 요청하고 그룹 사이에 고정 대기 간격을 적용. crontab으로 평일 야간·주말 주·야간 실행을 설정하고, 결과를 CSV로 가공·분류해 내부 서버로 전송

결과

배치 요청 간격과 실행 시간대를 조절해 운영. 고정 대기는 이전 그룹의 완료를 보장하지 않으며, 오류 감소율이나 실시간 성능 개선 수치는 별도로 측정하지 않음

A부서

Nexacro 연동 중 파일 수신 방식을 변경

원인

기존 @RequestParam("ocrFiles") MultipartFile[] 방식에서 파일 수신 문제가 발생. 필드명 불일치인지 클라이언트의 요청 구성 때문인지는 확인된 기록만으로 단정하기 어려움

해결 과정

고정 필드명에 대한 파라미터 바인딩 대신 MultipartHttpServletRequest의 getFileNames()로 필드명을 순회하고 getFile(name)으로 파일을 조회·저장. 크기가 0인 파일은 제외

결과

수신 로직을 고정 필드명 바인딩에서 파일 필드 순회 방식으로 변경. Spring의 Multipart 파싱을 사용하며, 별도의 파서를 직접 구현한 것은 아님

    추출 정확도 확인. 문서 17종을 유형별 최소 100건씩 현업에서 육안 검증했으며, 부서별 평균 약 95%로 평가했다. OCR 엔진·스키마·보정 로직을 포함한 최종 추출 결과의 평가다.

  • 안정성

    대량 처리 안정성을 고려한 운영. 그룹 간 요청 간격과 평일 야간·주말 스케줄을 적용해, 실시간 업무 시간대를 고려한 배치 운영 절차를 마련했다.

  • A부서

    수기 입력 부담 절감. 담당자가 문서를 보며 직접 입력하던 심사 항목을 자동 추출·기입 구조로 전환해 반복적인 수작업 부담을 줄였다.

  • B부서

    모델 개발 데이터 기반 마련. 과거 문서를 자동 OCR 처리해 raw 데이터로 적재하는 구조를 구축, 이후 자체 모델 개발의 학습 데이터 기반을 마련했다.

05

회고 · 배운 점

DESIGN

같은 엔진, 다른 두 개의 설계

동일한 AIOCR 엔진을 연동하더라도, 부서의 업무 특성(실시간성 vs. 대량 처리)에 따라 응답 방식과 실행 전략을 다르게 선택해야 한다는 것을 배웠다. 요구사항을 먼저 "동기적 사용자 경험이 필요한가"와 "처리량이 우선인가"로 구분해 접근한 것이 설계 방향을 잡는 데 핵심이었다.

ASYNC

비동기 콜백을 다루는 감각

상태 폴링으로 고객사의 동기 응답 요구를 연결했다. 다만 분석이 길어질수록 요청 대기 시간과 상태 조회가 늘어나므로, 유사한 시스템에서는 타임아웃 정책과 작업 ID 기반 비동기 조회 방식을 함께 검토할 필요가 있다.

OPERATIONS

운영까지 고려한 배치 설계

배치 실행 시간과 요청 간격도 업무 요구사항의 일부임을 배웠다. 당시에는 고정 대기와 시간대 분리로 운영했으며, 처리 시간 편차가 큰 환경에서는 완료 상태를 확인해 다음 그룹을 요청하는 방식을 개선안으로 검토할 수 있다.
