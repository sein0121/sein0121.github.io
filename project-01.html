PROJECT 01 · 2024.02 — 2024.08 · 팀 프로젝트 (백엔드 3인)

주문 처리 시스템 MSA 전환

모놀리식 구조로 운영되던 주문 서비스를, 트래픽 증가와 배포 지연 문제를 해결하기 위해 도메인 단위 서비스로 분리하고 이벤트 기반 아키텍처로 전환했습니다.

GitHub ↗ 아키텍처 문서 ↗

OVERVIEW

주문 서비스는 회원, 상품, 결제 로직이 하나의 애플리케이션에 뒤엉켜 있어 배포 한 번에 20분 이상 걸리고, 특정 모듈의 장애가 전체 서비스 장애로 번지는 구조였습니다. 이 프로젝트에서는 주문 도메인을 독립된 서비스로 분리하고, 서비스 간 통신을 동기 호출에서 이벤트 기반으로 전환하는 작업을 리드했습니다.

PROBLEM

  • 피크 시간대(점심 12시) 트래픽이 평소 대비 8배 증가하며 응답 지연 발생
  • 결제 모듈 배포 시 주문 조회까지 함께 중단되는 강결합 구조
  • 장애 발생 시 어느 로직에서 실패했는지 추적하기 어려운 로그 구조

ARCHITECTURE

주문 생성 이벤트를 Kafka로 발행하고, 재고·결제·알림 서비스가 각자 이벤트를 구독해 처리하는 구조로 전환했습니다.

Client │ ▼ [Order Service] ──publish──▶ Kafka Topic: order.created │ │ ▼ ┌────────────┼────────────┐ [Order DB] ▼ ▼ ▼ [Stock Svc] [Payment Svc] [Notify Svc] │ │ │ [Stock DB] [Payment DB] (Push/Email)

이 구조를 넣어보고 실제 다이어그램/이미지로 교체하셔도 좋습니다. (draw.io, Excalidraw 등으로 그린 후 이미지 삽입 추천)

KEY DECISIONS

왜 동기 호출 대신 이벤트 기반을 선택했는가. 주문 생성 시점에 재고·결제가 즉시 확정될 필요는 없었고, 오히려 동기 호출 체인이 길어질수록 장애 전파 범위가 넓어지는 문제가 있었습니다. Kafka를 도입해 각 서비스가 독립적으로 재시도·복구할 수 있도록 설계했습니다.

데이터 정합성은 어떻게 보장했는가. 분산 트랜잭션 대신 Saga 패턴을 적용해, 실패 시 보상 이벤트(주문 취소)를 발행하는 방식으로 최종적 일관성을 확보했습니다.

TROUBLESHOOTING

전환 초기, Kafka Consumer의 처리 속도가 Producer를 따라가지 못해 메시지 적체가 발생했습니다. Consumer Group의 파티션 수를 늘리고, 처리 로직 중 I/O 대기 시간이 긴 알림 발송을 별도 큐로 분리하여 해결했습니다. 이 과정에서 병목 구간을 특정하기 위해 Kafka Lag 지표를 Grafana 대시보드로 시각화했습니다.

RESULTS

-65% 평균 응답 시간
20분 → 4분 배포 소요 시간
0건 전환 후 전체 장애

수치는 예시입니다. 실제 프로젝트의 배포 로그, 모니터링 지표(APM, Grafana 등)를 근거로 채워 넣으면 설득력이 훨씬 높아집니다.
