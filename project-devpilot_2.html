02

프로젝트 구조 · 아키텍처

Java/Spring 애플리케이션의 도메인과 인증 구조를 중심으로 설계하고, 실제 서비스 운영을 위해 CloudFront·EC2·Redis까지 연결했습니다.

전체 시스템 아키텍처
GitHub OAuth 로그인 요청 흐름
CI/CD 배포 파이프라인

설계 원칙 01 — 외부 시스템과 내부 도메인 분리

GitHub REST/GraphQL 응답을 그대로 노출하지 않고 서비스 도메인 모델로 변환해, 외부 API 스펙 변경이 내부 비즈니스 로직에 직접 전파되지 않도록 구성했습니다.

설계 원칙 02 — 책임과 트랜잭션 경계 분리

@Transactional self-invocation 문제를 분석한 뒤 서비스 책임과 트랜잭션 경계를 분리했습니다. 프록시 동작 방식에 의존한 우회보다 코드의 책임과 트랜잭션 범위를 명확히 하는 방향으로 개선했습니다.

설계 원칙 03 — 변경 가능한 의존성은 추상화

AI Provider 호출부를 AiRoadmapDraftClient 인터페이스로 분리해 특정 공급사에 대한 결합도를 낮췄습니다. 인프라 확장 역시 추측이 아니라 부하테스트 결과를 근거로 적용했습니다.

핵심 기술 의사결정
DB 인프라 — RDS → EC2 Docker MySQL

관리형 대비 추가 비용 없이 EC2 위에서 구성하고, 운영 부담은 직접 감수했습니다.

인증 — JWT → OAuth2 + Redis Session

SPA/모바일 API가 실제로 필요해질 때까지 JWT 도입을 보류했습니다.

AI 공급사 — OpenAI → Google Gemini

비용 우위를 택하고, 인터페이스를 추상화해 공급사를 교체할 수 있게 했습니다.

수평 확장 IaC — CDK → Terraform

선언적 IaC로 재현 가능하게 관리하고, ALB/ASG 검증 환경을 필요할 때 생성한 뒤 동일 코드로 제거했습니다.

부하테스트 — nGrinder/JMeter → k6

별도 서버 없이 JS 스크립트를 git으로 관리할 수 있어 선택했습니다.

03

트러블슈팅

Java/Spring 애플리케이션 설계와 실제 운영 과정에서 마주친 문제 중, 백엔드 개발자로서 설명 가치가 높은 사례를 중심으로 정리했습니다.

배포

Mixed Content 차단과 세션 쿠키 교차사이트 전달 실패

이슈 · 원인

프론트(CloudFront, HTTPS)와 백엔드(EC2 IP, HTTP-only)가 분리되어 있어 브라우저가 API 호출을 Mixed Content로 차단했습니다. 두 도메인이 달라 SameSite=None; Secure가 필요한 세션 쿠키도, 백엔드가 HTTP라 Secure 속성 자체가 성립하지 않아 전달되지 않았습니다.

해결 과정
  • CloudFront에 EC2를 두 번째 오리진으로 추가해 /api, /oauth2, /login 경로를 백엔드로 라우팅, 프론트·백엔드를 완전히 동일한 도메인으로 통합
  • Origin domain에 raw IP를 등록할 수 없어 nip.io로 우회 등록
  • CloudFront가 커스텀 오리진에 X-Forwarded-Proto를 자동 전달하지 않는 문제는 nginx에서 고정값 "https"로 하드코딩해 해결
결과
  • 도메인 구매 없이도 Mixed Content와 쿠키 교차사이트 문제를 근본적으로 해결
  • GitHub OAuth 로그인 플로우가 실사용 가능한 수준으로 정상 동작
Spring Session

Redis를 붙였지만 세션이 저장되지 않던 문제

이슈 · 원인

spring.session.store-type: redis 설정만으로는 Spring Boot 4.1 / spring-session-data-redis 4.x 조합에서 자동 활성화가 되지 않아, 배포 후 DBSIZE가 계속 0으로 유지되는 문제가 있었습니다.

해결 과정
  • SecurityConfig에 @EnableRedisIndexedHttpSession 명시적 애노테이션 추가
  • 배포 후 실제로 세션이 Redis에 저장되는지, 컨테이너 재생성 후에도 로그인이 유지되는지까지 검증
결과
  • 배포(컨테이너 재생성)마다 전체 사용자가 로그아웃되던 구조적 문제 해결
  • 이후 수평 확장 시 인스턴스 간 세션을 공유할 수 있는 기반 확보
운영 안정성

애플리케이션 빌드와 런타임 책임을 분리해 배포 위험 제거

이슈 · 원인

t3.micro(RAM 1GB) 위에서 SSH 접속 후 직접 git pull → docker build를 실행하는 수동 배포 방식이라, 컴파일 중 메모리 부족으로 서버가 응답 불가 상태에 빠질 위험이 상존했습니다.

해결 과정
  • GitHub Actions 러너에서 Docker 이미지를 빌드해 GHCR에 push하고, EC2는 이미지를 pull만 하도록 파이프라인 설계
  • deploy-backend.yml / deploy-frontend.yml / ci-check.yml 3개 워크플로우로 분리, PR 단계 빌드 검증과 branch protection 구성
  • 배포 전용 IAM 사용자로 자격 증명 분리 (루트 계정 Access Key 미사용)
결과
  • EC2에서 컴파일 자체가 사라져 OOM 재발 위험 사실상 해소
  • 배포 소요 시간이 수 분 단위에서 수십 초 수준으로 단축
성능 분석

800 동시 요청에서 지연 증가 — 애플리케이션부터 인프라까지 병목 범위 축소

이슈 · 원인

k6로 실제 DB 조회 API를 800 동시접속까지 부하테스트한 결과 p95 1.24초로 Threshold(1000ms)를 초과했고, backend CPU는 105~110%, load average는 최대 25.71까지 치솟았습니다.

해결 과정
  • Hibernate SQL 로그로 N+1 여부부터 배제 (엔티티당 쿼리 1회씩만 실행 확인)
  • HikariCP/Tomcat 스레드 풀을 서버 스펙에 맞춰 축소 튜닝했으나 p95 1.24s → 1.15s로 효과 미미
  • t3.micro(vCPU 1개)의 순수 CPU 물리적 한계로 결론
결과
  • 미들웨어 튜닝이 아니라 수평 확장이 필요하다는 결론을 데이터로 확정
  • 다음 단계(ALB+ASG 확장)의 방향과 범위를 명확히 설정
확장성

CPU 병목을 근거로 백엔드만 수평 확장하고 효과를 재측정

이슈 · 원인

병목이 backend CPU로 확인된 상황에서, 상시 비용을 발생시키지 않으면서 수평 확장 효과를 검증할 방법이 필요했습니다. MySQL/Redis는 CPU 여유가 있어 그대로 두고 backend만 확장하는 것이 데이터 근거상 타당했습니다.

해결 과정
  • Terraform으로 ALB → ASG(backend 여러 대) → 기존 EC2(MySQL/Redis, private IP) 구조를 1회 구축
  • CloudFront 오리진을 ALB DNS로 임시 교체해 동일한 800 동시접속 시나리오로 재측정
  • 측정 종료 후 terraform destroy로 전량 삭제, 오리진 원복, IAM 권한도 최소 권한으로 되돌림
결과
  • ASG 3대 기준 p95 176ms(7배 개선), 처리량 599.6 req/s(3.6배 증가)로 Threshold 통과
  • 상시 운영하지 않고 terraform destroy로 정리해, 재현 가능한 IaC 자산만 남김

01

Java/Spring 기반 서비스의 인증·외부 연동·도메인 경계를 직접 설계

Spring Security OAuth2와 Redis Session으로 인증 상태를 관리하고, GitHub REST/GraphQL 응답을 내부 도메인으로 변환했습니다. AI Provider와 트랜잭션 경계도 책임 단위로 분리해 변경 영향 범위를 줄였습니다.

02

데이터 기반 성능 병목 분석부터 IaC 기반 수평 확장 검증까지 수행

k6 부하테스트로 CPU 병목을 확인하고, Terraform으로 ALB + Auto Scaling Group을 생성해 검증한 뒤 정리하는 방식으로 p95 응답시간을 약 7배 개선(1.24s → 176ms)하고, 처리량을 약 3.6배 증가(167 → 599.6 req/s)시켰습니다.

03

개발한 백엔드를 실제 배포하고 운영 관점에서 검증

EC2/S3/CloudFront와 GitHub Actions 기반 배포 환경을 구성하고, Redis 세션·부하테스트·IaC 실험까지 이어가며 로컬에서 동작하는 코드가 아니라 운영 가능한 서비스 관점으로 검증했습니다.

05

회고 · 배운 점

Java/Spring 기능을 구현하는 것에서 끝나지 않고, 왜 이 책임을 분리해야 하는지, 트랜잭션과 외부 의존성의 경계를 어디에 둘지, 운영 환경에서 병목이 생기면 어떤 순서로 검증할지를 고민한 프로젝트였습니다.
배움 01 — Spring의 동작 원리를 코드 구조에 반영

@Transactional self-invocation처럼 애노테이션을 붙이는 것만으로 해결되지 않는 문제를 경험하며, Spring Proxy와 트랜잭션 경계를 이해하고 서비스 책임 자체를 분리하는 것이 중요하다는 점을 배웠습니다.

배움 02 — 외부 의존성은 경계에서 격리

GitHub API와 Gemini를 직접 비즈니스 로직에 결합하지 않고 변환 계층과 인터페이스를 두면서, 외부 스펙이나 Provider가 바뀌어도 핵심 도메인의 변경을 최소화하는 설계를 경험했습니다.

배움 03 — 성능 개선은 측정과 가설 검증의 반복

N+1, 커넥션 풀, 스레드 풀을 차례로 확인한 뒤 CPU 한계로 병목 범위를 좁혔고, 수평 확장 후 동일 조건으로 재측정했습니다. 튜닝 자체보다 근거를 가지고 다음 선택을 하는 과정이 중요하다는 점을 배웠습니다.
