이커머스 API 서버

상품 조회부터 장바구니, 주문, 결제까지 이어지는 커머스 도메인 전체를 설계하고 구현한 REST API 서버입니다. 설계 문서와 API 명세를 함께 관리했습니다.

GitHub ↗ Swagger 문서 ↗

OVERVIEW

실무에서 자주 마주치는 커머스 도메인을 처음부터 끝까지 직접 설계해보고 싶어 시작한 프로젝트입니다. 상품, 옵션, 재고, 장바구니, 주문, 결제 상태 관리까지 포함한 API를 구현하고, Swagger로 문서화했습니다.

PROBLEM

  • 상품 옵션(사이즈, 색상 등) 조합에 따른 재고 관리 로직 설계
  • 동시에 여러 사용자가 같은 상품을 주문할 때 발생하는 재고 초과 판매 문제
  • 주문 상태(결제 대기 → 완료 → 배송 → 취소)의 일관된 상태 전이 관리

ARCHITECTURE

도메인을 상품, 주문, 결제 3개의 모듈로 분리하고, 계층형 구조(Controller-Service-Repository)로 설계했습니다.

[Controller] │ ▼ [Service] ──────▶ 비즈니스 로직 / 트랜잭션 경계 │ ▼ [Repository (JPA)] │ ▼ [MySQL] * 재고 차감은 비관적 락(Pessimistic Lock)으로 동시성 제어

KEY DECISIONS

동시 주문 시 재고 초과 판매를 어떻게 막았는가. 낙관적 락으로 먼저 시도했으나 재시도 로직이 복잡해져, 재고 차감처럼 충돌 빈도가 높은 구간에는 비관적 락을 적용해 단순하고 확실하게 정합성을 보장했습니다.

API 문서화를 어떻게 관리했는가. Swagger(springdoc-openapi)를 도입해 코드와 문서가 어긋나지 않도록 어노테이션 기반으로 자동 생성되도록 구성했습니다.

TROUBLESHOOTING

비관적 락 적용 후 특정 인기 상품에 요청이 몰릴 때 응답 지연이 발생했습니다. 락 범위를 상품 전체가 아닌 옵션(재고) 단위로 좁혀 잠금 경합을 줄였고, 이후 부하 테스트에서 응답 시간이 개선된 것을 확인했습니다.
