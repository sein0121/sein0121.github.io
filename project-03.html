01

프로젝트 요약

배경. 기존의 정산 방식은 계산부터 송금 확인까지 모든 과정이 수작업으로 이루어져 막대한 마찰 비용이 발생합니다. 식당 선결제 후 여행이 끝나면 엑셀이나 계산기로 1/N을 계산하고, 영수증 캡처를 단톡방에 공유한 뒤 일대일로 대조합니다. 카드사 더치페이는 ‘계산’에 국한되고, 실제 송금과 완료 증빙은 여전히 유저의 몫입니다. 반복되는 수작업 때문에 여행의 즐거움보다 정산의 스트레스가 커지는 상황을 PayTrip이 풀고자 했습니다.

Google Cloud x Solana Foundation 해커톤에 3인으로 참여한 사이드 프로젝트입니다. 그룹 채팅과 결제 내역을 RAG로 분석해 Gemini가 인당 정산 금액을 계산하고, x402 프로토콜을 통해 Solana devnet에서 USDC 자동 송금까지 처리합니다. 계산만 하는 일반 정산 챗봇과 달리, 계산·자율 실행·온체인 검증을 한 루프로 묶는 것을 목표로 했습니다. 저는 그 중 x402 결제 사이클, 재사용 가능한 결제 모듈·API 서버, LangGraph 에이전트 결제 연동과 서명 검증을 담당했습니다.

기존 서비스의 한계

카드사 더치페이는 ‘계산’에 국한되며, 실제 송금과 완료 증빙은 여전히 유저의 몫.

02

프로젝트 구조 · 아키텍처

PayTrip은 단순 계산을 넘어 실제 온체인 송금과 검증까지 완결하는 자율 AI 에이전트입니다. RAG·LangGraph·x402를 결합해 인식(Perceive) → 추론(Reason) → 실행(Act) → 증빙(Prove) 루프를 구성했고, 제가 담당한 결제 구간은 HTTP 402 핸드셰이크로 “결제가 확인되어야만 정산 완료”가 되도록 붙였습니다.

PHASE 01

임베드

PHASE 02

선결제

PHASE 03

자율 정산

03

트러블슈팅

담당했던 결제 구간에서 구현·검증한 세 가지입니다.

x402

HTTP 402 챌린지-응답을 송금·검증까지 한 사이클로

이슈 · 원인

정산이 끝나려면 결제 요청만으로 송금을 믿으면 안 되고, USDC 전송과 서명, 체인 확인이 같은 사이클 안에서 끝나야 했습니다.

해결 과정
  • 결제 요청 → USDC 송금 → 서명 재요청 → devnet RPC 검증 순으로 HTTP 402 챌린지-응답을 구성
  • x402 프로토콜 전체 사이클을 end-to-end로 구현하고 검증
결과
  • 402 핸드셰이크가 온체인 검증까지 이어지는 한 흐름으로 동작함을 확인
Payment

재사용 가능한 결제 모듈과 x402 API 서버

이슈 · 원인

에이전트 그래프 안에 송금 로직을 묻어두면 프로토콜을 따로 시연하거나 다른 경로에서 재사용하기 어려웠습니다.

해결 과정
  • 재사용 가능한 결제 모듈을 분리
  • Flask 기반 x402 API 서버를 구축해 핸드셰이크를 HTTP로 노출
결과
  • 결제 모듈과 API 서버를 에이전트와 독립적으로 호출·검증할 수 있게 됨
Agent

LangGraph 연동과 위조·정상 서명 검증

이슈 · 원인

에이전트가 정산 실행 단계에서 결제를 호출할 때, 서명만 있으면 통과시키는 방식으로는 위조 서명을 걸러낼 수 없었습니다.

해결 과정
  • LangGraph 에이전트에 결제 플로우를 연동
  • 위조 서명과 정상 서명 케이스를 나눠 검증
  • Solana Explorer에서 온체인 거래 증빙을 확보
결과
  • 에이전트 실행 결과가 서명 검증과 Explorer 증빙까지 연결됨
04

주요 성과

01

x402 프로토콜 전체 사이클을 end-to-end로 구현·검증

HTTP 402 챌린지-응답 사이클(결제 요청 → USDC 송금 → 서명 재요청 → devnet RPC 검증)을 한 흐름으로 동작하게 만들었습니다.

02

재사용 가능한 결제 모듈과 Flask x402 API 서버 구축

결제 로직을 모듈로 분리하고 Flask 기반 API 서버로 프로토콜을 노출해, 에이전트 밖에서도 같은 사이클을 호출할 수 있게 했습니다.

03

에이전트 연동과 온체인 거래 증빙 확보

LangGraph 에이전트에 결제 플로우를 붙이고, 위조/정상 서명 케이스를 검증했으며 Solana Explorer로 온체인 거래 증빙을 남겼습니다.

05

회고 · 배운 점

담당 범위는 x402 전체 사이클을 end-to-end로 붙이고, Flask API와 LangGraph 결제 연동에서 위조·정상 서명을 가린 뒤 Solana Explorer로 온체인 거래 증빙을 남기는 일이었습니다.
배움 01

x402는 상태 코드 하나가 아니라, 결제 요청 → 송금 → 서명 재요청 → RPC 검증이 끊기지 않아야 하는 프로토콜입니다. 이 사이클을 end-to-end로 붙여 본 것이 핵심이었습니다.

배움 02

결제 모듈과 API 서버를 에이전트와 분리해 두니, 프로토콜 자체와 에이전트 연동을 따로 검증할 수 있었습니다.

배움 03

위조 서명과 정상 서명을 나눠 보고, Solana Explorer로 거래를 열어보는 과정이 “보냈는가”에 대한 답을 코드 밖의 증빙으로 남기는 방법이었습니다.
