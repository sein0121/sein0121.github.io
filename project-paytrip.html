01

프로젝트 요약

배경. 그룹 여행에서 여러 사람이 비용을 선결제하면 정산 금액을 계산한 뒤에도 송금과 거래 확인을 따로 진행해야 합니다. 팀은 사전 구축한 여행 시뮬레이션 데이터를 바탕으로 정산 계획과 테스트 네트워크 송금을 연결했습니다.

담당. 저는 Flask 기반 결제 API와 재사용 가능한 USDC 송금 모듈을 개발했습니다. 결제 기능을 독립적으로 실행·검증한 뒤, 팀원에게 호출 계약과 LangGraph 노드 호출 예제를 제공해 통합을 지원했습니다.

02

전체 구조와 담당 결제 흐름

전체 서비스는 여행 팩트 조회 → Python 정산 계산 → 송금 실행 → 결과 요약 순서입니다. LangGraph가 단계를 연결하고 Gemini는 정산 설명과 보고서를 생성합니다. 아래에는 제가 개발·검증한 로컬 결제 흐름을 자세히 표시했습니다.

담당 구현 — HTTP 402 기반 결제 데모
Python · Flask · Solana devnet
1. 결제 조건 확인
GET /reserve/<item_id>402 + PAYMENT-REQUIRED가격·수신 주소 파싱선택적 예산 상한 검사
2. USDC 송금
송신·수신 토큰 계정 확인수신 계정이 없으면 생성금액 단위 변환 · transfer_checked거래 서명·RPC 제출
3. 서명 재요청
동일 URL + PAYMENT-SIGNATURERPC get_transaction 조회Confirmed 조건 · 결과 존재 확인200 + 데모 응답

x402의 결제 요구·증빙 제출 개념을 적용한 단순화된 데모입니다. 실제 예약 업무를 처리하는 API는 아니며, 원본 서버의 확인 범위는 제출한 거래가 RPC에서 조회되는지까지입니다.

직접 개발한 모듈

call_paid_api()가 HTTP 흐름을 처리하고, execute_travel_payment()가 송금 결과를 구성하며, send_usdc()가 실제 송금을 실행합니다.

팀의 최종 통합

팀원은 송금 로직을 결제 클래스로 재구성했습니다. 최종 에이전트의 기본 경로는 HTTP 402 왕복 대신 결제·확인 함수를 직접 호출합니다.

03

주요 구현

API

결제 요구와 실제 송금을 HTTP 흐름으로 연결

구현 목적

결제 조건을 받은 뒤 송금하고, 제출한 거래를 조회한 결과에 따라 API 응답을 반환하는 흐름이 필요했습니다.

구현 내용
  • Flask에서 가격·수신 주소를 담은 402 응답 반환
  • 클라이언트에서 조건을 파싱하고 건당 가격 상한 검사
  • USDC 송금 후 거래 서명을 담아 재요청하고 RPC 조회
확인 결과

미결제·가짜 서명 요청의 402 응답과 정상 송금 후 재요청의 200 응답을 직접 확인했습니다.

Module

송금 로직 분리와 단계별 실패 결과 구성

설계 목적

에이전트 통합 전에도 결제를 독립적으로 실행·검증하고, 실패한 단계를 구분할 수 있도록 구성했습니다.

구현 내용
  • HTTP 호출·송금·결과 구성을 함수별로 분리
  • 토큰 계정 준비·정수 금액 변환·거래 서명과 제출 처리
  • 송금 후 API 재요청이 실패해도 서명과 Explorer URL을 반환 결과에 보존
협업 결과

입력·반환 구조와 호출 예제를 문서화해 팀원에게 전달했습니다. 팀원은 이를 바탕으로 에이전트의 결제 실행 구간에 통합했습니다.

05

회고 · 보완 방향

호출 계약의 중요성

결제 기능을 모듈로 분리하고 입력·반환 구조를 정리해, 팀원이 내부 송금 구현을 복사하지 않고 활용할 수 있도록 했습니다.

외부 연동의 실패 경계

송금 제출, 체인 조회, API 응답은 서로 다른 단계입니다. 송금 후 API가 실패했다고 전체 함수를 다시 실행하면 중복 송금이 발생할 수 있어, 거래 정보를 보존하는 것과 재실행을 안전하게 만드는 것은 구분해야 합니다.

서비스화 시 보완할 점

현재 서버는 금액·수신자·토큰과 주문의 일치 여부, 거래 실행 오류, 서명 재사용까지 검사하지 않습니다. 서비스화하려면 주문·거래 상태를 저장하고 결제 조건 검증과 중복 실행 방지를 추가해야 합니다.
